「高速Webサービス開発」ワークショップ

完成形の動くデモ（玄米茶サンプル）: https://genmaicha-back-demo.y-arai-a8a.workers.dev/ — このワークショップで、このような「LP（ランディングページ＝サービス紹介の1枚ページ）＋購入＋マイページ」の SaaS を自分の題材で作る。

ワークショップの目的・ゴール

前提知識（このワークショップで前提とすること）

  • Claude Code を使ったことがある（起動・依頼・承認/拒否の基本操作が分かる）
  • Git を用いた開発経験がある（ブランチ・commit・push が一通りできる）
  • ソフトウェア開発の基本知識がある（基本情報技術者試験程度）

目的

  • Claude（Design / Code）を使った開発フローを全3セクションで一周する
    • 「AI にどう頼むと良いものが出てくるか」の肌感をつかむ
  • デザイン → フロント → バックエンド → テスト → デプロイ → 機能拡張 という実務に近い開発サイクルを、AI を駆動しながら一通り体験する

題材: 各自が作りたい SaaS の MVP（事前に考えてきてもらう）

  • 題材は各自が作りたい SaaS を持ち寄る。「流れを体験するのが目的」なので題材は自由だが、サブスクリプション（月額/年額課金）を必須とする
  • ただし全3セクションで一周できるよう、MVP（Minimum Viable Product＝必要最小限の機能に絞った最初の製品版）に落とし込んでおく
  • 資料中の例「玄米茶」は説明用の共通サンプルである。自分の題材では、このページ構成・機能を自分のサービスに読み替える
  • 全3セクションで一周するため、Section 2 までは構成を盛りすぎない（拡張は Section 3 のオプションで）

必須機能（Section 2 までに作るものの最低ライン）

ライセンスキー（購入の証として発行する一意の文字列）の配布は、題材によらず全員共通の実装要件である。

参加前に、自分が作りたい SaaS の MVP をざっくり考えてくること。どんなサービスか、下の5機能をどう満たすかを決めておく。迷う場合は「玄米茶」をそのまま自分の題材にしてもよい。

Section 2 到達時点の見本（玄米茶サンプル）: https://testai-genmaicha.ha-toge.workers.dev/ — 下の5機能が動く状態がゴールである。

Claude Code のセキュリティ対策（最初に1回）

秘密を Claude に読ませない設定

よくある勘違い: 「.claudeignore を作る」→ Claude Code に .claudeignore は無い。正しくは .claude/settings.json の permissions.deny で「読み取り禁止」を宣言する。

プロジェクト直下に .claude/settings.json を作り、秘密ファイルへの Read を拒否しておく（.claude/ ディレクトリがなければ mkdir -p .claude で作成）:

{
  "permissions": {
    "deny": [
      "Read(./.dev.vars)",
      "Read(./**/.dev.vars)",
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./**/.env)",
      "Read(./**/.env.*)",
      "Read(./secrets/**)"
    ]
  }
}

security-guidance

Claude が生成したコードをバックグラウンドで自動セキュリティレビューするプラグインである。 25 種類以上の脆弱性クラスを継続的に見てくれる。

セキュリティレビュー範囲例:

  • SQL インジェクション: 入力値で SQL 文を書き換えられる穴
  • XSS: 悪意あるスクリプトを画面に混入させる攻撃
  • SSRF: サーバーに内部への不正リクエストをさせる攻撃
  • IDOR: 他人のデータを覗ける穴
  • 認可バイパス: ログインできた人が権限外のデータや操作に届いてしまう穴

メニューから入れる。まず次を実行:

/plugin

選択したら、有効化のため次を実行:

/reload-plugins
  • インストール後、リストに security-guidance が出るか確認する: 
    /plugin list
  • うるさく感じたら無効化できる（元に戻すときは disable を enable に）: 
    /plugin disable security-guidance

npm パッケージの取り込みを制限する

公開直後のパッケージは、乗っ取られたメンテナー権限で悪意あるコードが仕込まれていても発覚が追いついていないリスクがある。
プロジェクト直下に .npmrc を作り、公開から7日未満のパッケージを取り込まない設定と、インストール時の既知脆弱性チェックを必須化する設定を入れておく。

min-release-age=7
audit=true
2つの設定の意味を見る
  • min-release-age=7: 公開7日未満のバージョンは npm install の対象外にする（typosquatting（名前の似た偽パッケージ）・乗っ取りアカウントからの悪性パッケージが広まりやすい初動期間を避ける）
  • audit=true: npm install 実行時に自動で npm audit 相当の脆弱性チェックが走る（デフォルトで有効だが、明示しておくと誤ってオフにされにくい）

なぜ LP だけなのか
Claude Design はトークン消費量が多く、標準的なプランでは全ページ分を作り込む余裕がないため、今回は LP のデザインシステムに絞る（機能ページは SCREEN_SPEC.md で決めた仕様を Claude Code に実装させる）。トークンに余裕があれば全ページを Claude Design で作ることも可能である。

事前確認: モデルと Effort の設定・デザインシステムのリセット

Claude Design を開くと「Make something new」の一覧が表示される。ここでは「Product prototype」を選ぶ（Slides・Document 等は使わない）。

一覧の右上に「Design system: None」という表示がある。過去に使ったデザインシステム名が残っていることがあるので、「None」になっているか確認し、違えばリセットしてから始める。

[6] 自動テスト

ゴール: アプリが要件を守れているかを一つずつ確かめ、守れていない箇所を特定して直す。

自動テストの考え方

この工程は、テストを緑にすることを目標にしていない。 テストは、何も検査していなくても緑になる。 だから緑の本数を数えても、何を守れているかは分からない。

守るべきことを決め、一つずつ確かめて結果を書き残すところまでが、この工程である。

要件を決めるところから結果を判定するところまで、全部を AI に任せることはできない。 アプリを誰が使うか、何が起きたら困るかを知っているのは人間だけである。 そしてテストが落ちたとき、AI はアプリではなくテストのほうを緩めて通すことがある。

だから工程ごとに、AI に書かせる部分と人間が決める部分を分けてある。

流れ

工程やること
① テスト要件AI と壁打ちしながら、このサービスにおいて守るべきことを箇条書きにする
② テスト設計要件ごとに機能と発生し得る問題「どこが壊れていたらテスト要件を満たせないか」を整理し、表にする
③ テスト環境準備Vitest 設定など、テストのための実行環境を用意する
④ テスト項目作成表を渡してテストコードを作成する
⑤ テストコード実施バックエンドとフロントそれぞれでテストを実行する
⑥ テスト結果テストの結果の中でテストが通っていない項目の原因を切り分けする
⑦ コード修正フロント／バックエンドの不具合の場合、AI でコードを修正して再度テストを実施する

このうち人間がやるのは ① テスト要件 の壁打ち、② テスト設計 の表の確認、⑤ テストコード実施 の skipped 目視、⑥ テスト結果 の原因の判定である。書く作業はすべて AI が進める。

① テスト要件

大事な前提：① テスト要件と ② テスト設計は、新しいセッションで始める。
実装を書いたセッションのまま続けると、コンテキストに実装が残った状態で要件と期待結果を書くことになる。

このセッションに読ませるのは SCREEN_SPEC.md と、この ① テスト要件 で作る docs/TEST.md だけにして、実装コードは読ませない。

やること: AI に質問させながら、守るべきことを箇条書きに落とす。

  1. Claude Code に壁打ちを頼む。前提を人間が先に整理しておく必要はない。 
    このアプリのテスト要件を決めたい。壁打ちに付き合ってほしい。

まず、要件を決めるために必要なことを私に質問して。
わからないことは推測せず、必ず質問すること。
質問には次を必ず含めること。
・漏れたら一番困る情報は何か
・壊れたら・止まったら一番困る操作は何か

書くのは「アプリが守るべきこと」だけにする。
・主語はアプリか利用者にする。開発者やテストコードを主語にしない
  ○「他人のライセンスキーを返さない」
  ✕「新しい API にはテストを必ず書く」
・破られたときに利用者に何が起きるかを、1行で言えるものだけ
・テストの書き方、モックの方針、どこまでテストするかの範囲は書かない

決まったら docs/TEST.md の「## テスト要件」に箇条書きで書いて。
各項目は「〜してはいけない」「〜は必ず」の形にすること。

    「わからないことは推測せず質問して」の一行がないと、AI は「一般利用者向けの公開サービスと仮定して」と書いて先に進む。前提を想像で埋めれば、そこから導く要件も想像になる。

    主語を縛る3行がこのプロンプトの要である。「〜してはいけない」「〜は必ず」はコーディング規約の言い回しでもあるので、形だけ指定すると AI は開発者が守るルールを書く。「新しい API にはテストを必ず書く」「fetch は必ずモックに差し替える」といった項目が並び、② テスト設計で「どこが壊れていたら守られないか」を問うても答えられない。壊れる場所がアプリの中にないからである。

  2. AI との壁打ちによって出た候補を、破られたら何が起きるかを1行で言えるかという基準にかけて取捨する。

    「購入したキーが消えない」なら、破られたときに「金を受け取ってモノを渡していない状態になる」と言える。これは載せる。落ちるのは次のような候補である。

    • 表示が速い — 何秒から問題なのかを決めていないので、破られたかどうかが言えない
    • エラーが出ない — 何も起きていない状態と区別できないので、破られたかどうかが言えない

    落とした候補は消して終わりでよい。期待結果が書けないので、② テスト設計で表の行にならない。

  3. docs/TEST.md がこの形になったら ① テスト要件 は終わりである。載せると決めた項目が、そのまま並んでいる。 
    ## テスト要件

- ライセンスキーとメールアドレスを本人以外に返さない
- 購入が成立したらライセンスキーは必ず発行され、再読込しても消えない
- 同じ購入で二重にライセンスキーが発行されない
- 認証が必要な API は未認証のアクセスを拒否する
- 必須項目が空の入力を受け付けない

    「破られたら何が起きるか」を詰めると、どういうときに守られるべきかが決まるので、要件は条件つきの長い文になる。長さは気にしなくてよい。

ポイント:

  • ここで出た要件が以降すべての土台になるので、モデルは高精度なもの（Fable / Opus）を使う。Effort は既定の Medium で足りる
  • 書き終えた「## テスト要件」は、② テスト設計 以降で AI に書き換えさせない。上書きされると、② テスト設計で行を判定する根拠と、⑥ テスト結果で原因を帰属させる根拠が消える
  • 要件を数え上げきることは目標にしない。数え上げたかどうかを確かめる手段がないので、いくら時間をかけても終わったと判断できない

② テスト設計

やること: 要件1つを「壊れる場所」に分け、場所ごとに表の1行を作らせる。

  1. Claude Code に表を書かせる。 
    docs/TEST.md の「## テスト要件」と SCREEN_SPEC.md を読んで、
同じファイルに「## テスト項目」として表を追記して。

・要件1つについて「どこが壊れていたらこの要件が守られないか」を挙げ、
  挙げた場所ごとに1行を作る
・列は「番号 | 守る項目 | どこで確かめる | 前提条件 | やること | 期待結果 | 結果」
・番号は T-001 から始まる連番にする（要件ごとに振り直さない）
・「どこで確かめる」は 関数 / API / 画面 / 通し のどれか
・見る場所が違えば別の行にする（レスポンスを見る行と DB を見る行は分ける）
・前提条件は空欄にしないこと
・「結果」列は空欄のままにする
・「## テスト要件」は読むだけ。書き換えないこと
・期待値の根拠は要件と SCREEN_SPEC.md の記述に置き、実装コードから推測しないこと

    このプロンプトの中心は、どこが壊れていたらこの要件が守られないかを挙げさせるところにある。挙げるのは、自分が Section 1 と 2 で作った画面、API、DB の3層のどこかである。

    「購入したキーが消えない」というテスト要件は、

    • 画面が送信していない
    • API がリクエストを処理していない
    • DB に保存されていない
    • 保存したものが読み出せない

    という4箇所がテスト項目として挙がり、このテストのすべてが緑となる場合に「購入したキーが消えない」と推定することができる。

    また、例えば「API がリクエストを処理している」ことのみしかテスト項目に挙げないで検証をすると、「テストを緑にしたにもかかわらず正しく動作しない」ということになりかねない。

    テスト設計を行うと、このような表となる（玄米茶サンプル。自分のアプリでは中身が変わる。ここでは要件2つ分だけ抜粋しており、実際は ① テスト要件 で書いた要件すべてについて行が続く）。

    テスト項目の表の例を見る
    番号守る項目どこで確かめる前提条件やること期待結果結果
    T-001購入したキーが消えない画面購入フォームを表示有効なメールで送信発行 API が呼ばれる
    T-002購入したキーが消えないAPIそのメールの記録が DB にない発行 API を叩く成功レスポンスにキーが入る
    T-003購入したキーが消えないAPI同上発行後に DB を直接見るキーが1件保存されている
    T-004購入したキーが消えないAPIT-003 の状態そのメールで取得 API を叩く保存したキーが返る
    T-005キーを本人以外に返さないAPIA 購入済み、B 未購入B でライセンス取得 APIA のキーが返らない
    T-006キーを本人以外に返さない画面同上B でマイページを開くA のキーが出ない
  2. 人間が確認する。見るものが2つあるので、順番に見る。
    順見るものやること
    1観点の抜け挙げた場所が足りているか。「購入したキーが消えない」に DB の行がない等
    2テストしなくていい箇所挙げた場所のうち、確かめるコストに見合わないものを落とす

「どこで確かめる」の4種: 環境と必要なパッケージは ③ テスト環境準備で入れる。

語叩く場所見る場所コマンド
関数関数を直接呼ぶ戻り値npm test

ポイント:

  • 前提条件の列を空欄のまま ④ テスト項目作成に進めない。空欄だと、AI は初期状態を用意するコードを書かない。前のテストが残したデータがそのまま残り、テストはそれを見て通ってしまう
  • 同じことを確かめられるなら、テスト範囲が狭いほうを選ぶ。関数がいちばん狭く、API、画面、通しの順に範囲が広がり、実行時間も書く手間も増える
  • 番号は、AI にテスト名の先頭へ入れさせる。⑥ テスト結果 で表の行とテストコードを照合するために使う

③ テスト環境準備

やること: ② テスト設計 で作った表の「どこで確かめる」列に出てきた種類（通しについては今は除外）だけ、実行環境を作らせる。

ここから実装のセッションに戻る。この ③ テスト環境準備 以降は実装コードを読ませてよい。

④ テスト項目作成

やること: 表をそのまま渡して実装させる。表にないことはさせない。

docs/TEST.md の「## テスト項目」の表に従ってテストを実装して。

・テスト名の先頭に表の番号を入れる（例: test('T-003 発行後に DB にキーが1件保存されている', ...)）
・「期待結果」列の値をそのまま使い、実装コードから推測しないこと
・表にない項目を勝手に足さないこと

⑤ テストコード実施

この工程で分かるのは、表のどの行が緑で、どの行が赤かである。 赤が出てもここでは直さない。原因の切り分けは次の ⑥ テスト結果 でまとめてやる。 1本ずつその場で直すと、診断と修正が同じやりとりに混ざり、AI がテストの期待値を緩めて緑にする道を選べるようになる。

出力の skipped が0件であることを、人間が自分で見る。 skipped があってもテスト全体は成功として扱われるので、画面は緑のまま、確かめた本数だけが足りなくなる。

skipped は test.skip や it.todo と書いてあるときに出る。④ テスト項目作成 のプロンプトで禁止したのに出ていたら、AI がテストを通せずに逃げ道を使ったということである。

ここでコミットする: このあと ⑦ コード修正 ではテストファイルが変わっていないことを git の差分で確かめる。git に追跡されていないファイルは差分が出ないので、先にコミットしておかないと、テストが改変されていても気付けない。

docs/TEST.md とテストコードとテストの設定をコミットして。
このあと git で確認するので、私が言うまで追加のコミットはしないこと。

⑥ テスト結果

やること: 表とコードを突き合わせ、落ちた原因を切り分ける。直すのは次の ⑦ コード修正 である。

  1. 表とテストコードを番号で突き合わせる。 
    docs/TEST.md の「## テスト項目」の表にある番号と、
テストコードのテスト名に入っている番号を突き合わせて、
どちらか片方にしかない番号を挙げて。

出力はそのまま見せること。要約しないこと。判定はこちらでする。
    • 表にあってコードにない → ② テスト設計 で作った行が ④ テスト項目作成 で落とされている（「通し」の行は実装していないので、ここに出るのが正しい）
    • コードにあって表にない → AI が勝手に足している
  2. 赤が出たときだけ、落ちた原因を切り分けさせる。全部緑ならこの手順と次の修正は飛ばして、結果列の記入へ進む。この時点では直させない。 
    落ちているテストの原因を切り分けて。次の3つのどれかで判定して。

・実装が要件を満たしていない
・テストの書き方が悪い
・要件そのものが間違っている（実装もテストも正しいが、要件の記述がずれている）

判定だけ報告して。まだ何も直さないこと。

    診断と修正を1回のやりとりでまとめて頼むと、AI は実装を直すより手数の少ない道、つまりテストの期待値を緩めて緑にする道を選べる。判定だけを先に受け取り、何を直すかは人間が決める。

    「要件そのものが間違っている」と判定された行は、人間が要件を直す。そのうえで表の期待結果も直し、④ テスト項目作成 からやり直す。

ポイント:

  • 「どこで確かめる」が「通し」の行は、ここでは赤にも緑にもならない。④ テスト項目作成 で除外しているためである
  • 落ちた行が出ること自体は成果である。「作ったつもりが作られていなかった」という発見だからである

⑦ コード修正

やること: ⑥ テスト結果 の判定にもとづいてフロント／バックエンドを直し、再度テストを実施して、結果を表に書き残す。

  1. 直す対象を指示する。テストファイルは変更禁止だと明示する。 
    T-005 の原因は認可の抜けなので、backend の実装を直して。
テストファイルは変更しないこと。

    直させたら再実行し、赤だった行が緑に変わったことを確認する。

  2. 判定と修正の結果を、表の「結果」列に埋めさせる。行数が多いので人が手で書かない。 
    docs/TEST.md の「## テスト項目」の表の「結果」列を埋めて。

・緑だった行は「緑」
・落ちた行は「落ちた → 原因 → どう直したか」
・「どこで確かめる」が「通し」の行は「[13] で確認予定」
・空欄を残さないこと
・「結果」列以外は書き換えないこと

    書かせたあと、判定が自分の見立てと合っているかを人間が読む。結果列を埋めると、次のような表となる（② テスト設計 に載せた抜粋には無い行も含めた例）。

    結果列を埋めた表の例を見る
    番号守る項目結果
    T-002購入したキーが消えない緑
    T-003購入したキーが消えない落ちた → 保存処理が未対応 → 実装を直して緑
    T-005キーを本人以外に返さない落ちた → 認可の抜け（バグ）→ 実装を直して緑
    T-007必須項目が空の入力を受け付けない落ちた → 要件の書き間違い（名前は任意でよかった）→ 要件と期待結果を直して緑
    T-009同じ購入で二重に発行されない未修理 → 二重発行のガードが無い（時間切れ・持ち帰り）
    T-008キーを本人以外に返さない[13] で確認予定（通しの行）

    要件を壊れる場所ごとに分けて行にしてあるので、落ちた行がそのまま原因の場所を指す。T-001 が落ちたなら画面、T-003 が落ちたなら保存処理である。

    結果列は、落ちた時点で止めずに、直したところまで書く。「落ちた」で終わっている行は、まだ作業が残っている行である。

    「通し」の行は ④ テスト項目作成 で除外しているので、結果列に「[13] で確認予定」と書く。空欄のままにしない。空欄は「まだ判断していない」を意味するので、確かめていないことが記録から消える。

    git diff --stat -- '*.test.ts' '*.test.tsx'

    ここに差分が出ていたら、直されたのはアプリではなくテストである。

  4. 差分の確認が済んだら、ここまでをコミットする。 
    テスト工程の修正と docs/TEST.md の更新をコミットして。

ポイント:

[8] メール機能の実装（Resend）★☆☆

お題: 問い合わせ通知メール／ライセンスキー送付メールを実装する
学び: 外部 API 連携の基本形・Secrets 管理

Resend とは

メールを送るための API を提供する SaaS である。自分で SMTP サーバを用意する代わりに、HTTP リクエスト1本でメールを送れる。

この課題で使う理由は、送信結果をダッシュボードのログで1件ずつ追えることにある。届かなかったときに、原因がアプリ側にあるのか送信側にあるのかを切り分けられる。

サービス側の準備

  1. https://resend.com/login で Google SSO ログインする
  2. 左タブ API keys → Create API Key（権限は Sending access で十分である。Sending domain は All domains を選択する。名前は各自で決めてよい）
  3. 発行された API キーを手元にコピーしておく（.dev.vars への投入は、次の「実装〜確認」で変数名が決まってから行う）

送信ドメインはどうする？（ここがつまずきやすい）

独自ドメインから送るには DNS 検証（ドメインの所有者であることを DNS レコードの設置で証明する作業）が必要で、それは自分のドメインが決まる公開後の話である。ワークショップでは次の方針を推奨：

  • 動作確認は Resend のテスト用アドレス onboarding@resend.dev を From に使う
    • 「自分宛に届く」を確認するには十分である
  • 独自ドメインからの送信は任意（やりたい人だけ、デプロイ後に DNS を設定）

重要: この From はドメイン検証なしで送れるが、宛先は Resend に登録したアカウントのメールアドレス1つだけに限られる。それ以外のアドレスに送ると Resend がエラーを返す。

API キー作成時のスコープ設定について（本ワークショップでの方針）
Resend の API キー作成画面では「Sending domain」を絞り込めるが、本ワークショップでは "All domains" を選んで作成すること。独自ドメインを別途追加・DNS 検証しないと特定ドメインのキーが発行できず、手順が止まってしまう。

実装〜確認

  • From / To をどうするかも含めて AI に相談して実装する。
    あわせて「この機能に要る環境変数を .dev.vars.sample に追記して」と依頼し、確定した変数名で .dev.vars（backend/ 直下のローカル用環境変数ファイル。無ければ新規作成）に、サービス側の準備で取得した API キーを入れる（例 RESEND_API_KEY=...）。

  • 送ったら Resend ダッシュボードの Logs で Status を確認する
  • 200 以外が出たら、エラー本文をそのまま AI に渡して直す
  • 本番でも使うなら、RESEND_API_KEY を本番側にも設定してデプロイ（[8][9][10] 共通の手順参照）

Stripe とは

オンライン決済を代行する SaaS である。カード情報は Stripe がホストする決済画面で預かるので、自分のアプリはカード番号を受け取らない。決済が完了したことは Webhook（Stripe から自分のサーバへ送られてくる通知）で知る。

この課題で使う理由は、テストモードがあることにある。本物の課金を発生させずに、購入からライセンス発行までを何度でも通せる。

③ ローカルで Webhook を検証する

前提: stripe.ts / license.ts の実装（AI への依頼）が完了してから進む。実装が未完了の場合は先に「Checkout セッションを作成する API エンドポイントと Webhook 受信エンドポイントを実装して」と AI に依頼する。

ローカル環境では Stripe から直接 Webhook が届かない（インターネットに公開されていないため）。Stripe CLI の stripe listen を使って、Stripe のイベントを手元のバックエンド（npm run dev の出力に表示されているポート）に転送する必要がある。

ターミナルを2つ使う。バックエンド（npm run dev）を起動したまま、別ターミナルで stripe listen を動かす。

  1. 別ターミナルで Stripe CLI の listen を実行する（転送先は、実際にバックエンドが起動しているポートに置き換える）: 
    stripe listen --forward-to localhost:<バックエンドのポート>/webhook/stripe
  2. listen 開始時に表示される Webhook 署名シークレット（whsec_...）を .dev.vars にセット（例: STRIPE_WEBHOOK_SECRET=whsec_...）して npm run dev を再起動（stripe listen は止めなくてよい。バックエンドのターミナルだけ Ctrl+C → 再起動）
  3. テストカードで購入して、購入 → Webhook 受信 → ライセンス発行までローカルで通す
    • テストカード番号は 4242 4242 4242 4242（有効期限＝未来の任意の日付／CVC＝任意の3桁）
    • テストモードのため実際の課金は行われない。ただし本物のカード番号は受け付けられずエラーになるため、必ず上記のテストカード 4242 4242 4242 4242 を使う

④ 本番（デプロイ後）に Webhook を設定する

ここでの「本番」はデプロイ後の公開環境を指す。Stripe を live mode（本物の課金）に切り替えるわけではなく、③と④のどちらも終始テストモードのままである。
③と④で署名シークレットが別物になるのは、Webhook の転送先 URL が違うためである。

  1. デプロイ前に、ローカルの .dev.vars に入れた値（Secret key・Price ID など）を本番側にも設定しておく（wrangler secret put / ダッシュボード）。※ Webhook 署名シークレットだけは本番用を後から（手順6）入れる
  2. 本編 [7] の手順で Cloudflare にデプロイする
  3. Stripe ダッシュボードの検索窓で「Webhook を作成」を検索して進む
  4. checkout.session.completed は必須で選ぶ（他に必要なイベントは AI に聞いて選ぶ）
  5. エンドポイント URL に、自分の Worker の Webhook 受信 URL（パスまで含めた URL）（例 https://<name>.workers.dev/webhook/stripe）を入力する
  6. 作成後に表示される本番用の署名シークレットを取得 → Cloudflare の環境変数に投入（ダッシュボードなら Secret タイプで。共通の秘密情報の置き場所参照）
  7. 本番で決済を確認する

⑤ 購入後の戻り先とマイページ表示（つなぎ込み）

  • Checkout には決済後の戻り先 URL（success_url / cancel_url）が要る。成功時は Section 2 で作った /success ページにつなぐ（AI に「購入後 /success に戻して」と頼めばよい）
  • 「マイページにライセンスが出る」ための紐付けに注意:
    • Webhook で発行したライセンスは購入者の emailに紐づく。マイページはログイン中ユーザーの email でライセンスを引く
    • [10] Clerk をやらない場合は、Section 2 のモック認証の email（ヘッダ x-user-email）と購入時の email を一致させること。ここがズレると「購入したのにマイページに出ない（別人扱い）」になる。
      具体的には、フロントのリクエストヘッダ X-User-Email に固定値（例: test@example.com）をセットし、Stripe Checkout の customer_email にも同じ値を渡せば一致する

⚠️ ハマりどころ

  • 署名シークレットはローカル（③）と本番（④）で別物である（転送先 URL が違うため。Stripe をテストモードから切り替えるわけではない）。混同しない
  • 署名検証は実装の細部（「生のリクエストボディ」で検証する等）でつまずきやすい。自分でコードを追わず、「Stripe の署名検証が公式推奨の方法（生のリクエストボディでの検証）で実装されているか確認して」と AI に点検させる
  • 二重発行防止: Stripe は同じイベントを複数回送ってくることがある。同じ購入イベントが2回届いてもライセンスを1件だけ発行するように実装する（処理済みのイベント ID を記録して、既に処理済みなら無視する）
  • email の不一致で「マイページに出ない」が起きやすい（上記の紐付けを参照）

✅ 完了の定義

テストカードで購入 → マイページにライセンスが表示されれば完了である。余裕があれば二重発行防止まで確認する。ローカルで動作確認できたら、wrangler secret put でシークレットを本番に投入して npm run deploy までを完了とする。

[10] ID 連携機能の実装（Clerk）★★☆

お題: ログイン必須のマイページ（未ログイン → サインインへリダイレクト）
使うもの: @clerk/clerk-react（フロント）＋ Hono 側で Clerk の認証トークンを検証
学び: トークンの検証をバックエンドでやる理由。フロントの見た目だけの保護は意味がない

Clerk とは

ログインの仕組みをまるごと引き受ける SaaS である。サインイン画面、Google などの外部アカウントとの連携、セッションの管理を用意してくれる。自分で書くのは、届いたトークンを検証する部分だけになる。

このトークンは JWT（JSON Web Token）と呼ばれ、ログイン済みであることを証明する。検証すれば、そのリクエストが本当にログイン済み本人からのものかを確かめられる。

この課題で使う理由は、認証を自作するとパスワードの保存やセッションの失効で間違えやすく、その間違いがそのまま脆弱性になることにある。

ログイン（Clerk）まで組み込んだ動くデモ（玄米茶サンプル）: https://testai-login.ha-toge.workers.dev/
このデモでは、未ログインで /mypage を開くとサインイン画面へリダイレクトされ、Google でログインするとマイページが表示される、というところまでが動く（Clerk 開発モード）。

Section 2 でモック認証にしておいた GET /api/me（ハンドラ＝リクエストを受けて処理する関数。backend/src/routes/me.ts など）を、本物の Clerk 認証に差し替える課題である。Claude Code に『Section 2 のモック認証を Clerk トークン検証に差し替えて』と指示するだけで進められる。

サービス側の準備

  1. https://dashboard.clerk.com/ で Google SSO ログインする
  2. アプリケーションを作成する。作成画面で Application name（後でいつでも変更可）と Sign in options（サインイン方法）をその場で選べる。
    ここで Email・Phone number・Username をオフ、Google をオンにする（メール認証は使わず Google SSO のみにする）。設定できたら、右側のプレビューが「Continue with Google」だけになっているか確認する。
    なおこの設定はダッシュボードから後でいつでも変更できるので、作成後に直しても構わない。
  3. Configure → Instance → API keys から2つのキーを手元にコピーしておく。ただし env への投入は、次の「実装メモ」で AI にパッケージを導入させたあとに行う。
    変数名は @clerk/* の規約で下表のとおりに固定されている。そして2つのキーで置き場所が違うのがポイントで、ここを間違えやすい。
    キー置き場所性質
    Publishable keyフロントの env（Vite なら frontend/.env に VITE_CLERK_PUBLISHABLE_KEY=...）。加えてバックエンドの backend/.dev.vars にも同じ値を CLERK_PUBLISHABLE_KEY=... で置く（@hono/clerk-auth がバックエンド側でもこのキーを要求するため。本番も同様に投入）公開してよい
    Secret keyローカル: バックエンドの backend/.dev.vars / 本番: Cloudflare ダッシュボードの環境変数（Secret タイプ）または wrangler secret put CLERK_SECRET_KEY秘密。漏らさない

実装メモ

  • 必要なパッケージ（フロント @clerk/clerk-react ／ バックエンド @hono/clerk-auth）も AI が導入してくれる。導入できたら、サービス側の準備でコピーした2つのキーを上表のとおり env にセットして npm run dev を（再）起動する
  • フロントはアプリを <ClerkProvider> で包み、サインイン UI を置く。未ログインなら /mypage に入れないようガードする
  • JWT 検証は @hono/clerk-auth が推奨（バックエンドでのトークン検証が一気に楽になる）
  • バックエンドは必ずトークンを検証してから保護 API を返す（フロントの出し分けだけでは保護にならない）
  • Section 2 のモック認証（ヘッダ x-user-email を信頼）を、この Clerk トークン検証に差し替えるのがゴール
  • 余裕があれば: マイページだけでなく購入（ライセンス発行）系の API も認証必須にし、購入者の email をクライアント入力ではなく検証済みトークンから取得する（認証なしだと他人の email を名乗ってライセンスを発行できてしまい、[12] セキュリティで指摘される穴になる）

Clerk ダッシュボード自体への管理者ログインは Google SSO で行う（手順1〜3）。参加者が自分のアプリにサインインする際も、上記の設定（メール認証オフ・Google SSO オン）が適用されるので Google アカウントでサインインする。

⚠️ ハマりどころ

  • 本番（デプロイ後）でサインインが弾かれるときは、Clerk ダッシュボードに公開ドメイン（https://<name>.workers.dev）を許可オリジンとして登録する

✅ 完了の定義

以下をすべて満たしたら完了:

  • ローカル確認: 未ログインで /mypage を開くとサインイン画面に誘導される（入れない）
  • ローカル確認: 未ログイン状態で GET /api/me を叩くと 401（未認証＝「ログインしていないので拒否した」という HTTP ステータス）が返る（AI に「未ログインで /api/me を叩いて 401 になるか確認して」と依頼すればよい）。サインイン後は /mypage に自分の情報が表示される
  • 本番へのシークレット投入: backend/.dev.vars に記入済みのシークレットのみを wrangler secret put で本番側に投入する（上の「置き場所を分ける」表を参照）
    • フロントの VITE_CLERK_PUBLISHABLE_KEY は frontend/.env からビルド時に埋め込まれるため、wrangler への投入は不要。npm run deploy のビルドで自動反映される
  • 本番確認: npm run deploy 後、本番 URL（https://<name>.workers.dev）でサインイン → /mypage が表示される
    • サインインが弾かれる場合は、上の⚠️ハマりどころにある許可オリジンの登録を行う

[11] 運用保守★☆☆

お題: 公開後の運用を体験する。扱うのは監視、ログ、障害特定、対策、コストの5つ
実装先: .claude/skills/（運用スキルを Claude Code に作らせる）
学び: 公開後の「運用」を Claude Code のスキルで仕組み化する

まず: Cloudflare API トークンを用意する

wrangler だけだと取得できる情報に制限がある。ログ集計やコスト試算には API トークンが要る。

  1. Cloudflare ダッシュボード右上のアイコン → Profile を選択する
  2. 左メニューの API Tokens → Create Token をクリックする
  3. 「Create Custom Token」の Get started をクリックする
  4. Token name を入力し、Permissions を Account / Account Analytics / Read にして作成する
  5. 取得したトークンを backend/.cf-ops.token に保存（例 CLOUDFLARE_API_TOKEN=... の1行）。.dev.vars とは別ファイルにする（理由は下記）。.gitignore に .cf-ops.token を追加しておく

このトークンは Worker が使うのではなく、運用スキルが shell からファイルを読んで使う（Cloudflare の集計 API（GraphQL）を叩くため）。

ここで注意したいのが置き場所である。.dev.vars は Section 1 の設定で Read を拒否しているので、スキルが cat 等で読もうとするとブロックされる。

そこで運用トークンだけは deny 対象外の別ファイル（.cf-ops.token）に分離する。ここに入れるのは Analytics 読み取り専用の低権限トークンなので、Stripe/Clerk 等の高価値シークレット（.dev.vars）とは分けて扱ってよい。

なお本番 secret に入れる必要はない（ローカルにあれば十分）。また、トークンが無くても wrangler tail のライブログは見られる。トークンが必須なのは集計・コスト試算だけである。

運用チェックを「スキル」にする

Claude Code のスキルとは、.claude/skills/<名前>/ ディレクトリに必要なファイルを置くことで、「運用チェックして」のような自然言語で呼び出せる専用コマンドを登録できる機能である。

なお [5] で使った /code-review などの「組み込みスキル」は最初から入っているスキルで、Section 1 で入れた security-guidance のような「プラグイン」は、スキルなどをまとめて配布するパッケージにあたる。

毎回同じ確認をスキル（.claude/skills/）にしておけば、「運用チェックして」の一言で再利用できる。ここで作ってもらうスキルは次の5つ。

#スキルやること置き場所
1インフラ障害確認依存サービス（Cloudflare/Clerk/Stripe/Resend）の公開ステータスを確認.claude/skills/infra-status/
2ログ取得Cloudflare のログ／エラーを取得して問題がないか確認.claude/skills/cf-log-check/
3障害箇所の特定ログ・直近デプロイをソースと突き合わせて原因を絞る.claude/skills/fault-localize/
4対策・回避策ログ内容から恒久対策・暫定ワークアラウンドを出す.claude/skills/remediate/
5コストモニタリングrequests / CPU 時間からコストを試算.claude/skills/cost-monitor/

5つを一気通貫で回す統合スキル ops-check にまとめてもよい（.claude/skills/ops-check/）。いずれも Claude Code に作らせ、自分のサービス向けに調整する。

手順

  1. 上記の手順で API トークンを作成し、backend/.cf-ops.token に保存する（.dev.vars とは別ファイル。理由は上記）
  2. スキルを Claude Code に作ってもらう → 「運用チェックして」で実際に動くか確認する 
    .claude/skills/ 以下に、本番運用チェック用のスキルを5つ作って。
1. infra-status: Cloudflare/Clerk/Stripe/Resend の公開ステータスページを確認して障害有無をまとめる
2. cf-log-check: wrangler tail で本番 Worker のログ・エラーを取得して問題がないか確認する
3. fault-localize: ログと直近のデプロイ差分をソースと突き合わせて障害箇所を絞り込む
4. remediate: 特定した原因への恒久対策と暫定ワークアラウンドを提案する
5. cost-monitor: Cloudflare の GraphQL Analytics API で requests / CPU 時間を集計してコストを試算する

共通の前提:
- Cloudflare API トークンは backend/.cf-ops.token に CLOUDFLARE_API_TOKEN=... の形式で置いてある。
  集計が必要なスキルはこのファイルを読んで使う（.dev.vars は読まない）
- 使っていないサービス（Stripe/Clerk/Resend など）があれば対象から外して
- 5つを順に実行して結果をまとめる統合スキル ops-check も作って。「運用チェックして」で ops-check が動くようにして

✅ 完了の定義

5つのうち最低1つの運用スキルが動作する（「運用チェックして」で応答が返ること）。残りは持ち帰りで作ってよい。

[12] セキュリティ★★★

お題: 自分のアプリをセキュリティ観点で点検し、最低1つ直す
ツール: Claude Code（/security-review・常時の security-guidance）＋ SonarCloud
参考: [6] で作った docs/TEST.md の認証境界まわりのテスト（回帰テスト＝直した問題が再発していないかを毎回確かめるテスト。その土台にする）
学び: 「AI が書いたコード」を自分で点検できるようになる

見る観点

  • 認証境界（ログインなしで入れる範囲と、ログイン必須の範囲の境目）: 未認証／偽造 JWT で 401 になるか
  • IDOR（Insecure Direct Object Reference：権限のない他人のデータを横断参照できてしまう脆弱性）: 他人の email を body に入れても無視されるか（他人のデータを引けないか）
  • 機密のマスク: API レスポンスにフルのライセンスキーが含まれていないか

2通りの点検を併用する

  • Claude Code（/code-review・/security-review・security-guidance の基本は [5] レビューにまとめてある。ここではセキュリティ点検に実際に使う）
    • /security-review で差分・コードを点検させる（実行例は [5] レビューにある）
    • 事前に security-guidance を入れていれば、編集・コミットのたびに自動で点検されている（Claude Code セキュリティ対策参照）
  • SonarCloud（静的解析）

    SonarCloud は、静的解析（コードを実際に動かさずに、書かれた内容を読むだけで問題を見つける手法）を GitHub と連携して行う SaaS である。コードを push するたびにセキュリティ脆弱性・バグ・コード品質の問題を自動検出し、Claude Code の差分レビューでは気づきにくいパターンを補完する。

    初回のアカウント作成〜組織作成は手順が多いので、以下は実際の画面ひとつずつに沿って説明する。

    1. 点検対象を main ブランチに push（SonarCloud は main / PR を解析）
    2. https://sonarcloud.io にアクセスし、ログイン画面で 「GitHub」 を選ぶ
    3. GitHub 側の確認画面で 「Authorize」 をクリックし、SonarQubeCloud に GitHub アカウントの参照を許可する（ここはまだ本人確認だけで、リポジトリへのアクセス許可は次の手順）
    4. 初回は SonarCloud の 「Welcome」画面が表示されるので 「Get started with GitHub」 をクリックする
    5. 再び GitHub 側の画面に移り 「Install & Authorize SonarQubeCloud」が表示される。「Only select repositories」を選び、点検したいリポジトリだけにチェックを入れてから 「Install & Authorize」 をクリックする

      ⚠️ ここが一番の要注意ポイントである。「All repositories」を選ぶと、将来作るものも含めて GitHub 上のプライベートリポジトリすべてのコードが SonarCloud に見えるようになる（詳細は下記ハマりどころ参照）。

    6. SonarCloud に戻ると 「Create an organization」画面が表示される。
      • Name・Key を入力する。どちらも秘密情報ではないので、GitHub のアカウント名をそのまま使ってよい
      • 「Automatically import new GitHub repositories」はチェックしない。チェックすると新規リポジトリが自動で解析対象に追加されてしまう（下記ハマりどころ参照）
    7. 下にスクロールすると 「Enter payment details」でプランを選ぶ画面が続く。個人の小さな MVP なら無料枠で十分なので 「Free」（$0）を選ぶ（カード情報の入力は不要）
    8. 「Create organization」をクリックすると組織が作成され、Projects 画面に移る（最初は「No projects here yet」と表示される）
    9. 右上の ＋ → Analyze new project（前の画面の「Analyze a new project」ボタンからでも同じ画面に進める）
    10. 「Analyze projects」画面で Organization を確認し、点検したいリポジトリにチェックを入れて「Set Up」をクリックする
    11. 「Project onboarding」画面に切り替わり解析が自動で始まる。「We are analyzing your project」と表示されている間はそのまま少し待つ（数十秒〜数分程度）
    12. 解析が完了すると 「Summary」画面に切り替わり、Quality Gate（あらかじめ決めた品質基準を満たしているかを合否判定する仕組み）や項目ごとの指摘件数が表示される。表示される項目の意味は次のとおり（下図はあくまで一例の件数）:
      • Security（脆弱性）: 0 Open issues／評価 A（A が最良〜E が要改善の5段階）
      • Reliability（バグの可能性がある箇所）: 16 Open issues／評価 E
      • Maintainability（保守性・コードの読みやすさに関する指摘＝コードスメル）: 23 Open issues／評価 A
      • Coverage（テストカバレッジ）: 0.0%（別途設定しないと計測されない項目のため、今は未計測というだけ）
      • Duplications（重複コードの割合）: 0.0%
      ここに出た指摘を AI と一緒にレビューする（意味・直し方を AI に説明させる。具体的なやり方は次項）

指摘の中身を見て、AI と一緒にレビューする

「Summary」画面の数字（例: Reliability 16 Open issues）はあくまで件数の集計である。個別の指摘を開いて中身を見るのがレビューの本番である。

  1. 左サイドバーの 「Issues」をクリックするか、Summary 画面の指摘件数（例: 「16 Open issues」）を直接クリックすると、個別の指摘一覧に移る。
    • 左側の「Filters」で Software quality（Security / Reliability / Maintainability）ごとの内訳が確認できる
    • Severity でも絞れる。Blocker〜Info の5段階の緊急度で、Blocker が最も重大、Info が参考程度である
  2. 一覧から1件クリックすると、右側に 該当コードと SonarCloud による説明が表示される。上部に指摘内容・影響する Software quality・重大度（Blocker など）、下部のタブに切り替えると「Where is the issue?」（該当コード）・「Why is this an issue?」（理由の説明）が見られる
  3. その内容を Claude Code に見せる。下図のように詳細画面の5箇所（①〜⑤）に印を付けたので、そこをコピーしてプロンプトのひな形に埋めるだけでよい:

    ①〜⑤をそのままコピーして埋めて送る:

⚠️ ハマりどころ

  • SonarCloud の指摘には誤検知（false positive）もある。鵜呑みにせず AI と判断する
  • 解析対象を絞りたいので、このワークショップ用のリポジトリだけを対象にするのが推奨（Git ブランチ参照）
  • 意図しないリポジトリまで勝手に解析されることがある。原因は2つの組み合わせ:
    • SonarCloud の GitHub App を All repositories（全リポジトリ）で許可している
    • SonarCloud の Organization で新規リポジトリの自動取り込み（Automatic Analysis / auto-provisioning）が有効になっている

    この2つがそろうと、App から見えるすべてのリポジトリで、push のたびに SonarCloud が自動でプロジェクトを生成して解析する。プライベートリポジトリが含まれる場合はコードが外部に送られるため注意したい。

    誤って All repositories を選んでしまった場合は、次のどちらかで対処する。

    • すでに「All repositories」で許可してしまった場合は、あとから絞れる
      • 入口は https://github.com/settings/installations（メニューからたどるなら GitHub → Settings → Integrations → Applications → SonarCloud → Configure）
      • そこで Only select repositories に変更して対象を絞る
    • 個別プロジェクトだけ止めたいなら、SonarCloud の対象プロジェクト → Administration → Analysis Method の「Automatic Analysis」を OFF、または Administration → Deletion で削除

Playwright とは

ブラウザを実際に動かしてアプリを操作するテストツールである。付属の Codegen を使うと、自分が画面でやった操作がそのままテストコードとして書き出される。そのため、テストの書き始めでつまずかない。

[6] の Vitest が関数や API を単体で確かめるのに対して、Playwright は画面を通した一連の流れを確かめる。

流れ

  • ⓪ 準備
  • ① テストする行を2本決める
  • ② 操作を録画する
  • ③ 検証を足して実行する
  • ④ 赤の原因を決める（赤が出たときだけ）
  • ⑤ push する

このうち自分で考えるのは ① の行の選択と ④ の赤の判断。ほかは Codegen と AI が進める。

「何をテストするか」は [6] ② で決めてある。この章はそれを Playwright で実行に移す工程なので、決め直さない。

⚠️ [9] 決済 / [10] ID 連携 を実施済みの人は、⓪ 準備の前にここを読む

[10] を入れるとログインが Google の画面に移る。Playwright は Google のログイン画面を自動操作できないので、そのままでは認証が要る画面のテストが1本も書けない。

解決策は @clerk/testing である。ログイン画面を通らずに認証済みの状態を作る。

npm i -D @clerk/testing

1. テスト用ユーザを1人作る — Clerk ダッシュボードで作る。手順は4ステップである。

(1) メール認証を一時的に有効化する — Configure → User & authentication → Email。Google ログインしか有効にしていないと、次の画面でメール欄が使えない。「Sign-up with email」「Sign-in with email」を ON にして Save。

(2) Users タブで Create user を押す

(3) メールとパスワードを入れて作る

  • メールは e2e+clerk_test@example.com のように +clerk_test を付ける。付けないと「Enter a valid email address」で弾かれる
  • パスワードは任意である。通らなければ Ignore password policies にチェックを入れる。このパスワードは以降使わない（テストはログイン画面を通らないため）ので、どこにも保存しなくてよい

(4) メール認証を元に戻す — 同じ画面で両方 OFF にして Save。

2. 設定は AI に作らせる

@clerk/testing を使って、Playwright のテストを Clerk 認証済みの状態で走らせたい。

・テスト用ユーザのメールは環境変数 E2E_CLERK_USER_EMAIL から読む
・サインイン画面は操作しないこと（Google ログインなので自動操作できない）
・アプリの認証方式をあとから変えても壊れないようにすること
・認証状態は毎回のテスト実行時に作り直すこと
・認証状態のファイルは Git に入れないこと

下3行が効いている。「サインイン画面を操作しない」でログイン画面を通らない方式に、「認証方式を変えても壊れない」でパスワードや確認コードに依存しない方式に、「毎回作り直す」で期限切れしない作りに寄る。ファイル構成は指定しなくてよい。

3. 認証状態を作る — 環境変数を渡して実行する。

set -a; . ./backend/.dev.vars; set +a
export E2E_CLERK_USER_EMAIL='e2e+clerk_test@example.com'
npx playwright test --project=setup

これが緑になれば設定は正しい。ログイン画面を操作するコードが混ざっていれば、ここで止まる。

4. ② 操作の録画はこう起動する — 開いた瞬間からログイン済みになる。サインイン画面は出ない。

npx playwright codegen --load-storage=playwright/.clerk/user.json \
  -o tests/01-xxx.spec.ts http://localhost:8787/mypage

保存先のファイルは .gitignore に入れる（/playwright/.clerk/）。

⚠️ 手動でログインして --save-storage に保存する方法は取らないこと。

Google の画面を通るため、保存されるファイルに自分の Google アカウントのセッションが丸ごと入る。.google.com や .youtube.com のクッキーが数十個まとめて書き出される。

漏れたときの被害はアプリのアカウントではなく Google アカウントの乗っ取りである。しかも数日で期限切れになり、アプリが壊れていないのにテストが赤くなる。

上の方法なら保存されるのはこのアプリと Clerk のクッキーだけで、Google のものは入らない。

[9] 決済（Stripe）も実施済みの場合: 行の選び方は ① に書いた。ここで用意しておくのは購入済みのアカウントで、上の --load-storage で開いたブラウザから1回だけ手で購入すればよい（テストカード 4242 4242 4242 4242）。

保証項目[9][10] 実施前実施後
他人のデータが見えない⭕ 別のメールを打つだけ⭕ テスト用ユーザをもう1人作れば書ける
購入操作そのものが正しい⭕ 画面内で完結✕ Stripe の決済画面を通る
購入後の表示が正しい⭕⭕ 前提を「購入済み」に置けば書ける
未ログインで中身が見えない⭕ メール入力フォームが出るだけ⭕ サインイン画面への遷移として書ける

① テストする行を2本決める

やること: [6] ② の「## テスト項目」の表から、ブラウザで確かめる行を2本選ぶ。選んだ行の番号は、② で作る録画ファイルの名前になる。

「どこで確かめる」が「通し」の行があれば、それを使う。前提条件と期待結果は [6] ② で埋めてあるので、そのまま使える。選ばなかった行は結果列を「[13] で確認予定」のままにしておき、時間が余ったら足す。

通しの行が無い場合は、ここで2本作る。[6] ① の「## テスト要件」から、画面から DB までを通らないと破れないものを2つ選び、表に「通し」の行を足す。前提条件と期待結果は、同じ要件の「画面」の行を見れば書ける。足した行の結果列には「[13] で確認予定」と書いておく（③ の実行で上書きする）。

⚠️ 外部サービスの画面を通る行は、ここで外す。

Playwright は Google のログイン画面や Stripe の決済画面を自動操作できない。[9] や [10] を実施した人は、その画面を通らないと再現できない行が出てくる。

[10]（Clerk）の分は、⓪ 準備の前に置いた折りたたみ（[9][10] 実施済みの人向け）の @clerk/testing で回避できる。[9]（Stripe）の購入操作そのものは回避できないので、前提条件を「購入済みのアカウント」に置き、購入後の表示を見る行に振り替える。振り替えられない行は選ばず、結果列に「決済画面の内側なので E2E 対象外。Stripe の設定として確認する」と書く。決済画面の中の不具合は Stripe 側の設定に由来するので、直す先が自分のリポジトリにない。

完了: 表の行を2つ選べていて、それぞれ前提条件と期待結果が埋まっている。

② 操作を録画する

やること: ① で選んだ2行それぞれについて、1回ずつ録画する。必ずリポジトリのルートで実行する。

cd <リポジトリのルート>
npx playwright codegen http://localhost:8787/ -o tests/<ファイル名>.spec.ts

末尾のファイル名は自分で決める。 -o は「録画した結果をどこに書き出すか」の指定である。① で2本選んだので、名前も2つ要る。

名前の付け方: tests/<表の番号>-<何を守るか分かる短い名前>.spec.ts

名前の例を見る（玄米茶サンプル）
① で選んだ行ファイル名
T-008 キーを本人以外に返さないtests/T-008-other-user.spec.ts
T-010 購入したキーが消えないtests/T-010-key-persists.spec.ts
  • 置き場所は tests/ である。⓪ の準備で生成された playwright.config.ts に testDir: './tests' という行があり、この場所だけがテストの探索対象になっている。別の場所に置くと実行されない
  • 番号は表の行番号（T-005 など）に合わせる。そうしておくと、テストが落ちたとき表のどの行のことかすぐ分かる
  • 拡張子は .spec.ts である。この拡張子で終わるファイルだけがテストとして拾われる（.test.ts も可。.ts だけだと無視される）

⚠️ -o は実行した場所からの相対パス。

tests/ の中で実行すると保存先が見つからずに落ちる。録画した内容はそのまま消える。

録画中にやること: 表の「前提条件」列に書いた状態を、画面を操作して自分で作る。そのうえで「期待結果」を見る画面まで進む。

たとえば前提条件が「A は購入済み、B は未購入」なら、1回の録画の中で A として購入し、続けて B としてマイページを開くところまでを通しで操作する。前提条件を作る操作も録画に含める。

操作し終わったらブラウザを閉じる。閉じた時点でファイルが書き出される。

⚠️ 画面が自動で切り替わったときは、生成された goto を必ず見ること。

Codegen が書く goto は開いた URL ではなく、移動が終わったあとの URL になる。未ログインで /mypage を開くとサインイン画面に飛ぶが、そのとき生成されるのはこうなる。

// 開いたのは http://localhost:8787/mypage なのに…

このまま実行するとサインイン画面を開いてサインイン画面が出ただけのテストになり、確かめたかったことが消える。自分のアプリの URL に戻すのは ③ の検証追加でやる。

  • 赤が出た行について、直したか・仕様として認めたかを自分で決めた
  • 選ばなかった通しの行は、結果列が「[13] で確認予定」のまま残っている（空欄にしない）

[6] は「通し」以外の行を全部緑にするところまでを完了条件にしている。通しの行だけがこの章に回されているので、ここで結果列が埋まると TEST.md の表に空欄がなくなる。

なぜ [6] の自動テストとは別にやるのか（部品検査と試乗）

[6] のテストは部品を1つずつ台の上で検査する。E2E は組み上がったものに実際に乗ってみる。守っている場所が違う。

         画面(React) ─── HTTP ─── Worker(Hono) ── D1
[6]    ├────┤                   ├────────┤
[13]     ├───────────────────────────────────┤
                        ↑
              [6] はここを見ていない

[6] は経路の左半分と右半分を別々に固める（画面テストは HTTP をモック、API テストは外部 API をモック）。

ところがその2つが噛み合っているかは誰も見ていない。バックエンドが licenseMasked を返しフロントが license_masked を読んでいても、両方とも緑になる。

実際に起きうるバグ[6] のテスト[13] の E2E
フロントが項目名を綴り間違えて画面が空欄見逃す気づける
npm run build:front を忘れて古い画面が配信されている見逃す気づける
他人のメールで開いたとき前の人のキーが画面に残る見逃す気づける
画面に導線が無い API を誰でも叩ける気づける見逃す
連投時のレート制限が効かない気づける見逃す

E2E は [6] の置き換えではなく補完である。だから「通し」にしなかった行は [6] の関数・API・画面のテストが引き取る。

[14] 自動デプロイ（Workers Builds）★★☆

お題: git push するだけで Cloudflare へ自動的にビルド・デプロイされる状態にする（[7] の手動デプロイを卒業する）
ツール: Cloudflare ダッシュボードの Workers Builds（Git 連携によるビルド・デプロイの自動化機能）
前提: [7] で wrangler deploy による手動デプロイまで完了していること
学び: CI/CD の初歩と、モノレポ構成でのビルド設定の考え方

他の Section 3 オプションと違い、ここでの作業はすべて Cloudflare ダッシュボード側の設定で完結する。リポジトリのコードに変更を加える必要は無く、Claude Code に実装を依頼する場面も無い。設定が一度終われば、あとは普段通り git push するだけで、Cloudflare 側が自動でビルド・デプロイを行ってくれる。

連携手順

  1. Cloudflare ダッシュボード → 対象の Worker → Settings → Build から GitHub リポジトリを連携する
    1. サイドバー最上部の 「Account home」 を選択する
    2. 画面中央（検索バーの下あたり）に並ぶ一覧から、対象の Worker を選択する
    3. 画面上部のタブを 「Settings」 に切り替える
    4. 下にスクロールし、「Build」セクション内の GitHub ボタンを選択する

    ⚠️ リポジトリのアクセス範囲について: GitHub ボタンを押すと GitHub 側で「Install & Authorize Cloudflare Workers and Pages」という許可画面が出る。

    ここでも SonarCloud のときと同様に、必ず 「Only select repositories」 を選び、連携したいリポジトリだけを許可すること。「All repositories」を選ぶとプライベートリポジトリのコードすべてに Cloudflare がアクセスできる状態になってしまう。

  2. Cloudflare に戻ると「Connect to a repository」画面が開く。上部の Git account で自分のアカウント（複数の GitHub 組織に所属している場合は連携したいアカウント）を指定する。Repository は直前に許可したリポジトリが自動で選ばれる
  3. Path（Root directory）を backend に設定する（モノレポ構成のため。空のままにすると Cloudflare が自動生成した誤った設定でデプロイされてしまうので注意すること。詳細は下記ハマりどころ）
  4. Build command に npm install --prefix ../frontend && npm run build:front を設定する （フロントのビルドをここで行う。空のままだとフロントがビルドされない）
  5. Production branch を main に設定する（dev への push はプレビューのみになる）。
    ただし Git ブランチ の運用（dev→main マージ後に SonarCloud 解析）と組み合わせる場合は、マージがそのまま本番公開になる点に注意する。詳細は Git ブランチ を参照すること。

⚠️ ハマりどころ

  • Path（Root directory）を設定し忘れると、API が全滅する: このリポジトリは frontend/・backend/ に分かれたモノレポ構成になっている。
    そのため Path を空のままにすると、Cloudflare は「ルートに設定ファイルが無い」と判断し、cloudflare-workers-and-pages[bot] がリポジトリのルートに簡易的な wrangler.jsonc を自動生成して PR を送ってくることがある。
    この自動生成ファイルは静的配信専用で、API のルーティングも D1/KV のバインディングも含まない。だから誤ってデプロイされると /api/* が全滅（404）し、フロントも未ビルドの生ファイルが配信されてしまう。
    対策としてPath 設定を先に済ませ、もし該当 PR が来ていたらマージせずクローズすること
  • Build command を設定し忘れると、フロントがビルドされない: 既定の Deploy command は npx wrangler deploy だけで、これは vite build（フロントのビルド）を含まない。必ず上記手順3の Build command を設定する
  • デプロイ直後は数秒〜十数秒、変更が全世界のエッジサーバーに伝播しきっていないことがある。すぐにアクセスして 404 が出ても、少し待ってから再確認する

✅ 完了の定義

上記4つの設定を終えたら、何か軽微な変更（コメント追加など）をコミットして dev に push するだけで、Cloudflare ダッシュボードの Deployments に新しいビルドが自動的に現れることを確認する。これが確認できれば完了である。余裕があれば、dev → main にマージ・push し、本番 URL（workers.dev）にその変更が反映されるところまで確認する。

Workers Builds の動作確認用に、軽微な変更（コメント追加など）をコミットして dev ブランチに push して。

「高速Webサービス開発」ワークショップ

付録: Claude Code 認証切り替えガイド

対象: 普段は API キーで使っている人が、一時的に Claude Code サブスクに切り替え、用が済んだら API キーに戻すための手順である。

これだけ覚える: どのキーを使うかは ~/.claude.json の記録で決まる。 rejected にあるキーは無視されてサブスクが使われ、approved にあるキーは使われる（サブスクより優先）。切り替えとは、この記録を /config や起動時プロンプトで書き換えること。

認証の記録は ~/.claude.json にある

「どのキーを使う / 使わない」は ~/.claude.json の customApiKeyResponses に記録される。 approved（使うキー）と rejected（使わないキー）の2つの配列があり、キーは末尾20文字だけが記録される（フルキーは保存されない）。

キーの3つの状態

状態意味起動時の挙動
approvedこのキーを使う、と承認済みこの API キーで動く（サブスクより優先）
rejectedこのキーは使わない、と拒否済みキーを無視してサブスクで動く
newまだどちらも選んでいない「このキーを使う？」と確認が出る

① API → サブスク: 一時的にサブスクへ切り替える

普段の API キー運用から、一時的にサブスクを使い始めるときの手順である。

  1. Claude Code のセッション内でログアウトする（approved が空になり、古いサブスクのログインも消える）。 
    /logout
  2. Claude Code を起動しなおす。env に API キーが残っているので「このAPIキーを使うか？」と聞かれる。ここで 「2. No (recommended)」を選ぶ。 
    claude
  3. No を選ぶと、ログイン方法の選択画面が自動で表示される（/login を打つ必要はない）。「1. Claude account with subscription」を選び、ブラウザで claude.ai（Pro / Max 等）にログインする。
  4. 認証方式を確認する。claude.ai になっていれば成功である。~/.claude.json は approved が空・rejected に当該キーが入った状態になる。 
    /status

環境変数の API キーは 消さなくてよい（/logout が承認を外すのでサブスクが使われる）。ただし起動のたびに確認プロンプトが出るのが煩わしければ、そのシェルで unset ANTHROPIC_API_KEY しておくとプロンプトが出なくなる。

② サブスク → API: 普段の運用に戻す

サブスクの用が済んで、普段の API キーに戻すときの手順である。ゴールはキーを rejected から外すことである。/config の ON で rejected から外れ、approved として記録される。

  1. env に API キーがあることを確認する（無ければ設定）。普段 ~/.zshrc 等に書いてあるならそのままでよい。 
    export ANTHROPIC_API_KEY="sk-ant-xxxxxxxx"
  2. Claude Code を起動する。 
    claude
  3. API キーを有効化する。① の直後はキーが rejected に入っているため起動時プロンプトは出ない。/config を開き「Use custom API key」を ON にする（キーが未決定=new の場合は起動時に確認が出るので、そのときは「1. Yes」でもよい）。 
    /config
  4. 認証方式を確認する。API キー利用になっていれば成功である。~/.claude.json は approved に当該キーが入り rejected が空の状態に戻る（冒頭の ~/.claude.json の例と同じ状態）。 
    /status

一度「使わない」を選んでいると、キーは rejected に入っている。 /config の ON で自動的に approved へ移るので問題ない。手動でやるなら ~/.claude.json の customApiKeyResponses.rejected から 該当キーの末尾20文字のエントリを削除する（削除すると new に戻り、再度確認プロンプトが出る）。

確認とトラブルシュート

確認に使うコマンド

現在の認証方式を見る（Claude Code セッション内）:

/status

approved / rejected の登録件数を確認する（キーの値は表示されない）:

jq '.customApiKeyResponses | {approved:(.approved|length), rejected:(.rejected|length)}' ~/.claude.json

うまく切り替わらないとき

症状原因対処
サブスクにしたのに API のままキーが approved に残っている/logout、または /config のトグルを OFF
API にしたいのに使われないキーが approved に無い（new/rejected）/config を ON、または起動時プロンプトで「使う」
ログインしても接続が切れるANTHROPIC_AUTH_TOKEN / CLAUDE_CODE_OAUTH_TOKEN が env に残存（承認ゲート無しで効く）該当変数を unset して再起動
/logout しても API が消えない/login で入力・保存したキー（keychain）は logout で消えない/status でソースを確認し、/login でサブスクに入れ直す

秘密情報の扱い: API キーの値をチャットやコードに貼らない。git 管理下のファイルにも書かない。恒久設定は各自の ~/.zshrc 等にとどめる。

仕組み（詳細・読まなくても切り替えはできる）

認証の優先順位

複数の認証情報があると、上ほど優先される。

順位認証方式
1クラウドプロバイダの資格情報（Bedrock / Vertex 等）
2ANTHROPIC_AUTH_TOKEN（Bearer トークン）
3ANTHROPIC_API_KEY — ただし approved のときだけ採用
4apiKeyHelper スクリプト
5CLAUDE_CODE_OAUTH_TOKEN
6サブスクの OAuth（/login で保存）

ANTHROPIC_API_KEY は承認ゲートがあり、未承認なら無視されてサブスクにフォールバックする。一方 ANTHROPIC_AUTH_TOKEN / CLAUDE_CODE_OAUTH_TOKEN はゲートが無く、セットされていれば効く。

/logout が実際にすること

  • customApiKeyResponses.approved を空にする（承認済みキーが外れる）
  • サブスクの OAuth 資格情報を消す
  • オンボーディング状態をリセット → 次回起動で確認プロンプトが再表示される
  • rejected には何も追加しない。/login で保存した keychain 上のキーも消さない

2つの「キーの保管場所」

  • 環境変数 ANTHROPIC_API_KEY … 承認（approved/rejected）で制御する。本ガイドではこれを前提とする。
  • 保存キー primaryApiKey（macOS Keychain）… /login でキーを直接入力した場合の保管先である。/logout では消えない。env 運用なら基本使われない。

補足: --bare / CLAUDE_CODE_SIMPLE などの簡易モードや非対話実行（claude -p）では、確認プロンプトを出さずに env のキーを直接使う経路がある（＝承認ゲートを通らない）。通常の対話起動は承認ゲート経由である。
