完成形の動くデモ（玄米茶サンプル）: https://genmaicha-back-demo.y-arai-a8a.workers.dev/ — このワークショップで、このような「LP（ランディングページ＝サービス紹介の1枚ページ）＋購入＋マイページ」の SaaS を自分の題材で作る。

ワークショップの目的・ゴール

前提知識（このワークショップで前提とすること）

  • Claude Code を使ったことがある（起動・依頼・承認/拒否の基本操作が分かる）
  • Git を用いた開発経験がある
  • ソフトウェア開発の基本知識がある（基本情報技術者試験程度）

目的

  • Claude（Design / Code）を使った開発フローを全3セクションで一周する
    • 「AI にどう頼むと良いものが出てくるか」の肌感をつかむ
  • デザイン → フロント → バックエンド → テスト → デプロイ → 機能拡張 という実務に近い開発サイクルを、AI を駆動しながら一通り体験する

題材: 各自が作りたい SaaS の MVP（事前に考えてくる）

  • 題材は各自が作りたい SaaS を持ち寄る。「流れを体験するのが目的」なので題材は自由だが、次の2つを満たすこと
    • サブスクリプション（月額／年額課金）であること
    • 購入すると利用者に「購入の証」が1つ渡ること。呼び名は題材に合わせて決めてよい（ライセンスキー／API キー／ダウンロードコード／契約番号・注文番号など）
  • 作るのは下の5機能だけである。題材は5機能に収まる大きさまで削っておくこと
  • 迷う場合は「玄米茶」をそのまま自分の題材にしてもよい。資料中の「玄米茶」は説明用の共通サンプルで、自分の題材ではこのページ構成・機能を自分のサービスに読み替える

Section 2 までに作るものの最低ライン — 下の5機能をどう満たすかを、題材と一緒に事前に決めておく。

Section 2 到達時点の見本（玄米茶サンプル）: https://testai-genmaicha.ha-toge.workers.dev/ — 下の5機能が動く状態がゴールである。

Claude Code のセキュリティ対策（最初に1回）

秘密を Claude に読ませない設定

よくある勘違い: 「.claudeignore を作る」→ Claude Code に .claudeignore は無い。正しくは .claude/settings.json の permissions.deny で「読み取り禁止」を宣言する。

プロジェクト直下に .claude/settings.json を作り、秘密ファイルへの Read を拒否しておく（.claude/ ディレクトリがなければ mkdir -p .claude で作成）:

{
  "permissions": {
    "deny": [
      "Read(./.dev.vars)",
      "Read(./**/.dev.vars)",
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./**/.env)",
      "Read(./**/.env.*)",
      "Read(./secrets/**)"
    ]
  }
}

security-guidance

Claude が生成したコードをバックグラウンドで自動セキュリティレビューするプラグインである。 25 種類以上の脆弱性クラスを継続的に見てくれる。

セキュリティレビュー範囲例:

  • SQL インジェクション: 入力値で SQL 文を書き換えられる穴
  • XSS: 悪意あるスクリプトを画面に混入させる攻撃
  • SSRF: サーバーに内部への不正リクエストをさせる攻撃
  • IDOR: 他人のデータを覗ける穴
  • 認可バイパス: ログインできた人が権限外のデータや操作に届いてしまう穴

メニューから入れる。まず次を実行:

/plugin

選択したら、有効化のため次を実行:

/reload-plugins
  • インストール後、リストに security-guidance が出るか確認する: 
    /plugin list
  • うるさく感じたら無効化できる（元に戻すときは disable を enable に）: 
    /plugin disable security-guidance

npm パッケージの取り込みを制限する

公開直後のパッケージは、乗っ取られたメンテナー権限で悪意あるコードが仕込まれていても発覚が追いついていないリスクがある。
プロジェクト直下に .npmrc を作り、公開から7日未満のパッケージを取り込まない設定と、インストール時の既知脆弱性チェックを必須化する設定を入れておく。

min-release-age=7
audit=true
2つの設定の意味を見る
  • min-release-age=7: 公開7日未満のバージョンは npm install の対象外にする（typosquatting（名前の似た偽パッケージ）・乗っ取りアカウントからの悪性パッケージが広まりやすい初動期間を避ける）
  • audit=true: npm install 実行時に自動で npm audit 相当の脆弱性チェックが走る（デフォルトで有効だが、明示しておくと誤ってオフにされにくい）

なぜ LP だけなのか
Claude Design はトークン消費量が多く、標準的なプランでは全ページ分を作り込む余裕がないため、今回は LP のデザインシステムに絞る（機能ページは SCREEN_SPEC.md で決めた仕様を Claude Code に実装させる）。トークンに余裕があれば全ページを Claude Design で作ることも可能である。

事前確認: 作るものの種類・デザインシステムのリセット・モデルと Effort

Claude Design を開くと「What should we create?」の画面になり、中央にプロンプト入力欄、その下に作るものの種類がアイコンで並ぶ。ここでは 「UI mockups」 を選ぶ（Slides・Document・Wireframe 等は使わない）。

ゴール: フロントが完成したらすぐに公開 URL を手に入れる（バックエンドは Section 2 で繋ぐ）

流れ

手順1〜2（インストール〜 whoami）はブラウザ連携とアカウント確認があるため自分のターミナルで打つ。手順3〜4（ビルド〜デプロイ）は Claude Code に「ビルドしてデプロイして」と任せてよい（下のコマンドは自分で打つ場合の参考）。

  1. wrangler（Cloudflare の CLI ツール。デプロイやクラウド資源の作成をコマンドで行う）をグローバルインストールする: 
    npm install -g wrangler
  2. Cloudflare にログインする: 
    wrangler login

    • login でブラウザが開く → Cloudflare 上で「許可」する
    • whoami でログインできたか／想定アカウントかを確認する
    • 会社用・個人用など複数アカウントを持っている人は whoami で取り違えていないか必ず確認する（別アカウントに資源を作る事故を防ぐ）

    npm run build
  4. Cloudflare Workers にデプロイ: 
    wrangler deploy

    初回は wrangler.jsonc の name が Worker 名として登録される。2回目以降は同じコマンドで上書きデプロイされる。
    また、アカウントで初めての Worker デプロイでは workers.dev のサブドメイン（URL の <account> 部分）の登録を求められることがある。

  5. 発行された URL をブラウザで開いて LP が表示されることを確認 🎉（実際の URL は https://<name>.<アカウントのサブドメイン>.workers.dev の形。本資料では以降、短く https://<name>.workers.dev と表記する）

    ローンチ後に機能を足していく前提なら、最初の設計が効いてくる。特に先に決めておくべきなのは後から取り返しがつかないもので、下の表の6つである。後から変えられるもの（正規化の度合い・インデックス・API のレスポンスの形・画面・集計）は、走りながら決めてよい。

    論点なぜ後から取り返しがつかないのか
    記録の有無現在値だけを持って上書きしていると「いつ・何が起きたか」が残らない。後から購入履歴や変更履歴の画面が必要になっても、記録していなかった期間の分は作れない
    ID の選び方メールアドレスを主キーにすると、メール変更やアカウント統合で詰む
    削除の仕方物理削除したデータは戻らない（論理削除やアーカイブにするか）
    外部 ID の保存Stripe の customer / session の id を残していないと、後から突合できない
    冪等キーWebhook の再送を判別できず二重計上すると、後から真偽を分けられない
    単位・通貨・時刻タイムゾーンや丸めの扱いが混在したまま溜まると、遡って直せない

    ここを押さえずに走ると、機能追加のたびに「そのデータは残っていない」「この ID では紐付けられない」に突き当たり、移行スクリプトと欠損データの手当てに時間を取られる。

    • 購入を出来事として積んでいない … 現在値で持っているため、[9] の Stripe Webhook の再送に弱い（本来は冪等性が要る）
    • 検証がフロント側だけになりがち … API で弾けないと守れない。[6] の機能テストでここを確認する

    決めること中身
    識別子ユーザーや購入の主キーには、値が変わらない専用の id（サロゲートキー）を使う。メールアドレスは変更されるため主キーにしない

[6] 機能テスト

ゴール: アプリが要件を守れているかを一つずつ確かめ、守れていない箇所を特定して直す。

機能テストの考え方

この工程の目的は、テストを緑にすることではなく、守るべきことを決め、一つずつ確かめて結果を書き残すことにある。

アプリを誰が使うか、何が起きたら困るかを知っているのは人間だけである。さらにテストが落ちたとき、AI は問答無用でテスト条件を緩めて通すことがある。そのため要件を決めるところから結果を判定するところまで、全部を AI に任せることはできない。

流れ

工程やること
① テスト要件AI と壁打ちしながら、このサービスにおいて守るべきことを箇条書きにする
② テスト設計要件ごとに機能と発生し得る問題「どこが壊れていたらテスト要件を満たせないか」を整理し、表にする
③ テスト環境準備Vitest 設定など、テストのための実行環境を用意する
④ テスト項目作成表を渡してテストコードを作成する
⑤ テスト結果テストを実行し、通っていない項目の原因を切り分けする
⑥ コード修正⑤ の判定ごとに実装かテストを直し、再実行して、結果を表に書き残す

[8] メール機能の実装（Resend）★☆☆

お題: 問い合わせ通知メール／購入の証の送付メールを実装する
学び: 外部 API 連携の基本形・Secrets 管理

Resend とは

メールを送るための API を提供する SaaS である。自分で SMTP サーバを用意する代わりに、HTTP リクエスト1本でメールを送れる。

この課題で使う理由は、送信結果をダッシュボードのログで1件ずつ追えることにある。届かなかったときに、原因がアプリ側にあるのか送信側にあるのかを切り分けられる。

サービス側の準備

  1. https://resend.com/login で Google SSO ログインする
  2. 左タブ API keys → Create API Key（権限は Sending access で十分である。Sending domain は All domains を選択する。独自ドメインを追加・DNS 検証しないと、特定ドメイン向けのキーは発行できないためである。名前は各自で決めてよい）
  3. 発行された API キーを手元にコピーしておく（.dev.vars への投入は、次の「実装〜確認」で変数名が決まってから行う）

送信ドメインはどうする？（ここがつまずきやすい）

独自ドメインから送るには DNS 検証（ドメインの所有者であることを DNS レコードの設置で証明する作業）が必要で、それは自分のドメインが決まる公開後の話である。ワークショップでは次の方針を推奨：

  • 動作確認は Resend のテスト用アドレス onboarding@resend.dev を From に使う
    • 「自分宛に届く」を確認するには十分である
  • 独自ドメインからの送信は任意（やりたい人だけ、デプロイ後に DNS を設定）

重要: この From はドメイン検証なしで送れるが、宛先は Resend に登録したアカウントのメールアドレス1つだけに限られる。それ以外のアドレスに送ると Resend がエラーを返す。

実装〜確認

  • From / To をどうするかも含めて AI に相談して実装する。
    あわせて「この機能に要る環境変数を .dev.vars.sample に追記して」と依頼し、確定した変数名で .dev.vars（backend/ 直下のローカル用環境変数ファイル。無ければ新規作成）に、サービス側の準備で取得した API キーを入れる（例 RESEND_API_KEY=...）。
    入れたら npm run dev を（再）起動して、まずローカルで往復させる
  • 送ったら Resend ダッシュボードの Logs で Status を確認する
  • 200 以外が出たら、エラー本文をそのまま AI に渡して直す
  • 本番でも使うなら、RESEND_API_KEY を本番側にも設定してデプロイ（[8][9][10] 共通の手順参照）

✅ 完了の定義

まずローカルで、自分宛にメールが届くこと。そこまで確認できたら、wrangler secret put でシークレットを本番に投入し、npm run deploy して本番でも届けば到達点である。

お題: プラン購入（Stripe Checkout）→ Webhook で購入の証を自動発行
学び: Webhook の扱いで外せない2点

  • 二重発行防止: 同じイベントが再送されても、購入の証は1件だけ出す
  • 署名検証: 届いた Webhook が本当に Stripe から来たものかを確かめる

Stripe とは

オンライン決済を代行する SaaS である。カード情報は Stripe がホストする決済画面で預かるので、自分のアプリはカード番号を受け取らない。決済が完了したことは Webhook（Stripe から自分のサーバへ送られてくる通知）で知る。

この課題で使う理由は、テストモードがあることにある。本物の課金を発生させずに、購入から購入の証の発行までを何度でも通せる。

決済まで組み込んだ動くデモ（玄米茶サンプル）: https://testai-payment.ha-toge.workers.dev/
このデモでは、LP の「購入する」から Stripe Checkout（テストカード 4242 4242 4242 4242）を通り、マイページに購入の証が表示されるところまでが動く（Stripe テストモード）。

Section 2 で「自前発行」していた購入の証を、決済イベント起点の自動発行に置き換える課題である。手順が多いので 5 フェーズに分けて進める。

  • ① アカウント準備
  • ② プラン作成
  • ③ ローカル Webhook 検証
  • ④ 本番 Webhook 設定
  • ⑤ つなぎ込み

① アカウントとキーの準備

  1. https://dashboard.stripe.com/login で Google SSO ログインする
  2. サンドボックス（テストモード）はデフォルトで有効である。テストモードとは、本物の課金が発生しない Stripe の練習環境のことである。
    ワークショップは終始このモードで進める（[6] の「機能テスト」とは別物である）
  3. 必要な環境変数を AI に聞き、.dev.vars.sample に雛形を作る
  4. 検索窓で「API」と検索 →「開発者 > API キー」→ 標準キーのシークレットキー（sk_test_...）をコピーし、.dev.vars にセットする
  5. （Stripe CLI が未インストールの場合は前準備 ④ を参照してインストールしてから実行）ターミナルで stripe login を実行し、Stripe CLI を自分のアカウントで認証する

② プラン（商品）を作る

商品カタログ → ＋商品を作成で、月額・年額の2つの継続課金プランを作る（プラン名・金額は自分のサービスに合わせて決めてよい。以下は玄米茶サンプルでの例）：

プラン名（例）種別金額（例）請求
月額プラン継続¥300 JPY毎月
年額プラン継続¥3000 JPY毎年

[1] Claude Design や LP の料金セクションで月額・年額以外のプラン（3つ目のプラン等）を追加した場合は、その分だけここでも Stripe の商品を追加で作ること。LP 側の料金プランと Stripe 側の商品は数・内容を一致させる。

  • 作成後、各プランの Price ID（price_...）を控える
    • 下の図の手順のとおり、ワークベンチ（Stripe の開発者向け管理画面）のデータマップ（オブジェクトの関連図）から取得する。Checkout に渡すのはこの Price ID である
    • （prod_... は商品そのものの ID である。コードで使うのは price_... の方）
  • 2つの Price ID を .dev.vars にセット（例 PRICE_MONTHLY=price_... / PRICE_YEARLY=price_...）
  • 実装: 「Checkout セッションを作成する API エンドポイントと購入の証の発行ロジックを実装して」と Claude Code に依頼する

③ ローカルで Webhook を検証する

前提: ② の実装（AI への依頼）が完了してから進む。未完了の場合は先に「Checkout セッションを作成する API エンドポイントと Webhook 受信エンドポイントを実装して」と AI に依頼する。

ローカル環境では Stripe から直接 Webhook が届かない（インターネットに公開されていないため）。Stripe CLI の stripe listen を使って、Stripe のイベントを手元のバックエンド（npm run dev の出力に表示されているポート）に転送する必要がある。

ターミナルを2つ使う。バックエンド（npm run dev）を起動したまま、別ターミナルで stripe listen を動かす。

  1. 別ターミナルで Stripe CLI の listen を実行する（転送先は、実際にバックエンドが起動しているポートに置き換える）: 
    stripe listen --forward-to localhost:<バックエンドのポート>/webhook/stripe
  2. listen 開始時に表示される Webhook 署名シークレット（whsec_...）を .dev.vars にセット（例: STRIPE_WEBHOOK_SECRET=whsec_...）して npm run dev を再起動（stripe listen は止めなくてよい。バックエンドのターミナルだけ Ctrl+C → 再起動）
  3. テストカードで購入して、購入 → Webhook 受信 → 購入の証の発行までローカルで通す
    • テストカード番号は 4242 4242 4242 4242（有効期限＝未来の任意の日付／CVC＝任意の3桁）
    • テストモードのため実際の課金は行われない。ただし本物のカード番号は受け付けられずエラーになるため、必ず上記のテストカード 4242 4242 4242 4242 を使う

④ 本番（デプロイ後）に Webhook を設定する

ここでの「本番」はデプロイ後の公開環境を指す。Stripe を live mode（本物の課金）に切り替えるわけではなく、③と④のどちらも終始テストモードのままである。
③と④で署名シークレットが別物になるのは、Webhook の転送先 URL が違うためである。

  1. デプロイ前に、ローカルの .dev.vars に入れた値（Secret key・Price ID など）を本番側にも設定しておく（wrangler secret put / ダッシュボード）。※ Webhook 署名シークレットだけは本番用を後から（手順6）入れる
  2. 本編 [7] の手順で Cloudflare にデプロイする
  3. Stripe ダッシュボードの検索窓で「Webhook を作成」を検索して進む
  4. checkout.session.completed は必須で選ぶ（他に必要なイベントは AI に聞いて選ぶ）
  5. エンドポイント URL に、自分の Worker の Webhook 受信 URL（パスまで含めた URL）（例 https://<name>.workers.dev/webhook/stripe）を入力する
  6. 作成後に表示される本番用の署名シークレットを取得 → Cloudflare の環境変数に投入（ダッシュボードなら Secret タイプで。共通の秘密情報の置き場所参照）
  7. 本番で決済を確認する

⑤ 購入後の戻り先とマイページ表示（つなぎ込み）

  • Checkout には決済後の戻り先 URL（success_url / cancel_url）が要る。成功時は Section 2 で作った /success ページにつなぐ（AI に「購入後 /success に戻して」と頼めばよい）
  • 「マイページに購入の証が出る」ための紐付けに注意:
    • Webhook で発行した購入の証は購入者の emailに紐づく。マイページはログイン中ユーザーの email で証を引く
    • [10] Clerk をやらない場合は、Section 2 のモック認証の email（ヘッダ x-user-email）と購入時の email を一致させること。ここがズレると「購入したのにマイページに出ない（別人扱い）」になる。
      具体的には、フロントのリクエストヘッダ X-User-Email に固定値（例: test@example.com）をセットし、Stripe Checkout の customer_email にも同じ値を渡せば一致する

⚠️ ハマりどころ

  • 署名シークレットはローカル（③）と本番（④）で別物である（転送先 URL が違うため。Stripe をテストモードから切り替えるわけではない）。混同しない
  • 署名検証は実装の細部（「生のリクエストボディ」で検証する等）でつまずきやすい。自分でコードを追わず、「Stripe の署名検証が公式推奨の方法（生のリクエストボディでの検証）で実装されているか確認して」と AI に点検させる
  • 二重発行防止: Stripe は同じイベントを複数回送ってくることがある。同じ購入イベントが2回届いても購入の証を1件だけ発行するように実装する（処理済みのイベント ID を記録して、既に処理済みなら無視する）
  • email の不一致で「マイページに出ない」が起きやすい（上記の紐付けを参照）

✅ 完了の定義

まずローカルで、テストカードで購入 → マイページに購入の証が表示されること。そこまで確認できたら、wrangler secret put でシークレットを本番に投入し、npm run deploy して本番でも通れば到達点である。余裕があれば二重発行防止まで確認する。

[10] ID 連携機能の実装（Clerk）★★☆

お題: ログイン必須のマイページ（未ログイン → サインインへリダイレクト）
使うもの: @clerk/clerk-react（フロント）＋ Hono 側で Clerk の認証トークンを検証

Clerk とは

ログインの仕組みをまるごと引き受ける SaaS である。サインイン画面、Google などの外部アカウントとの連携、セッションの管理を用意してくれる。自分で書くのは、届いたトークンを検証する部分だけになる。

このトークンは JWT（JSON Web Token）と呼ばれ、ログイン済みであることを証明する。検証すれば、そのリクエストが本当にログイン済み本人からのものかを確かめられる。

この課題で使う理由は、認証を自作するとパスワードの保存やセッションの失効で間違えやすく、その間違いがそのまま脆弱性になることにある。

ログイン（Clerk）まで組み込んだ動くデモ（玄米茶サンプル）: https://testai-login.ha-toge.workers.dev/
このデモでは、未ログインで /mypage を開くとサインイン画面へリダイレクトされ、Google でログインするとマイページが表示される、というところまでが動く（Clerk 開発モード）。

Section 2 でモック認証にしておいた API を、本物の Clerk 認証に差し替える課題である。Claude Code に『Section 2 のモック認証を Clerk トークン検証に差し替えて』と指示するだけで進められる。

サービス側の準備

  1. https://dashboard.clerk.com/ で Google SSO ログインする
  2. アプリケーションを作成する。作成画面で Application name と Sign in options（サインイン方法）をその場で選べる。
    ここで Email・Phone number・Username をオフ、Google をオンにする（メール認証は使わず Google SSO のみにする）。設定できたら、右側のプレビューが「Continue with Google」だけになっているか確認する。
    なおApplication name もサインイン方法も、ダッシュボードから後でいつでも変更できるので、作成後に直しても構わない。
  3. Configure → Instance → API keys から2つのキーを手元にコピーしておく。ただし env への投入は、次の「実装メモ」で AI にパッケージを導入させたあとに行う。
    変数名は @clerk/* の規約で下表のとおりに固定されている。そして2つのキーで置き場所が違うのがポイントで、ここを間違えやすい。
    キー置き場所性質
    Publishable keyフロントの env（Vite なら frontend/.env に VITE_CLERK_PUBLISHABLE_KEY=...）。加えてバックエンドの backend/.dev.vars にも同じ値を CLERK_PUBLISHABLE_KEY=... で置く（@hono/clerk-auth がバックエンド側でもこのキーを要求するため。本番も同様に投入）公開してよい
    Secret keyローカル: バックエンドの backend/.dev.vars / 本番: Cloudflare ダッシュボードの環境変数（Secret タイプ）または wrangler secret put CLERK_SECRET_KEY秘密。漏らさない

実装メモ

  • 必要なパッケージ（フロント @clerk/clerk-react ／ バックエンド @hono/clerk-auth）も AI が導入してくれる。導入できたら、サービス側の準備でコピーした2つのキーを上表のとおり env にセットして npm run dev を（再）起動する
  • JWT 検証は @hono/clerk-auth が推奨（バックエンドでのトークン検証が一気に楽になる）
  • バックエンドは必ずトークンを検証してから保護 API を返す（フロントの出し分けだけでは保護にならない）
  • Section 2 のモック認証（ヘッダ x-user-email を信頼）を、この Clerk トークン検証に差し替えるのがゴール

Clerk ダッシュボード自体への管理者ログインは Google SSO で行う（手順1〜3）。参加者が自分のアプリにサインインする際も、上記の設定（メール認証オフ・Google SSO オン）が適用されるので Google アカウントでサインインする。

⚠️ ハマりどころ

  • 本番（デプロイ後）でサインインが弾かれるときは、Clerk ダッシュボードに公開ドメイン（https://<name>.workers.dev）を許可オリジンとして登録する

✅ 完了の定義

以下をすべて満たしたら完了:

  • ローカル確認: 未ログインで /mypage を開くとサインイン画面に誘導される（入れない）
  • ローカル確認: 未ログイン状態で GET /api/me を叩くと 401（未認証＝「ログインしていないので拒否した」という HTTP ステータス）が返る（AI に「未ログインで /api/me を叩いて 401 になるか確認して」と依頼すればよい）。サインイン後は /mypage に自分の情報が表示される
  • 本番への環境変数の投入: backend/.dev.vars に書いた CLERK_SECRET_KEY と CLERK_PUBLISHABLE_KEY の両方を wrangler secret put で本番側に投入する（上の「置き場所を分ける」表を参照）
    • Publishable key は公開してよい値だが、@hono/clerk-auth がバックエンド側で要求するので、本番の Worker にも入れないとトークン検証が動かない
    • フロント側の VITE_CLERK_PUBLISHABLE_KEY（frontend/.env の方）は、ビルド時に埋め込まれるため wrangler への投入は不要。npm run deploy のビルドで自動反映される
  • 本番確認: npm run deploy 後、本番 URL（https://<name>.workers.dev）でサインイン → /mypage が表示される
    • サインインが弾かれる場合は、上の⚠️ハマりどころにある許可オリジンの登録を行う

見る観点

  • 認証境界（ログインなしで入れる範囲と、ログイン必須の範囲の境目）: 未認証／偽造 JWT で 401 になるか

  • 過剰な情報の返却: API レスポンスに、その画面で見せる必要のない情報まで載っていないか（内部の顧客 ID、他人の集計値、テーブルの行をそのまま返している等）

2通りの点検を併用する

  • Claude Code（/code-review・/security-review・security-guidance の基本は [5] レビューにまとめてある。ここではセキュリティ点検に実際に使う）
    • /security-review で差分・コードを点検させる（実行例は [5] レビューにある）
    • 事前に security-guidance を入れていれば、編集・コミットのたびに自動で点検されている（Claude Code セキュリティ対策参照）
  • SonarCloud（静的解析）

    SonarCloud は、静的解析（コードを実際に動かさずに、書かれた内容を読むだけで問題を見つける手法）を GitHub と連携して行う SaaS である。コードを push するたびにセキュリティ脆弱性・バグ・コード品質の問題を自動検出し、Claude Code の差分レビューでは気づきにくいパターンを補完する。

    初回のアカウント作成〜組織作成は手順が多いので、以下は実際の画面ひとつずつに沿って説明する。

    1. 点検対象を main ブランチに push（SonarCloud は main / PR を解析）
    2. https://sonarcloud.io にアクセスし、ログイン画面で 「GitHub」 を選ぶ
    3. GitHub 側の確認画面で 「Authorize」 をクリックし、SonarQubeCloud に GitHub アカウントの参照を許可する（ここはまだ本人確認だけで、リポジトリへのアクセス許可は次の手順）
    4. 初回は SonarCloud の 「Welcome」画面が表示されるので 「Get started with GitHub」 をクリックする

      ⚠️ ここが一番の要注意ポイントである。「All repositories」を選ぶと、プライベートリポジトリのコードが SonarCloud に見えるようになる（詳細は下記ハマりどころ）。

      • 「Automatically import new GitHub repositories」はチェックしない。チェックすると新規リポジトリが自動で解析対象に追加されてしまう（下記ハマりどころ参照）

    11. 「Project onboarding」画面に切り替わり解析が自動で始まる。「We are analyzing your project」と表示されている間はそのまま少し待つ（数十秒〜数分程度）

      • Reliability（バグの可能性がある箇所）: 16 Open issues／評価 E

指摘の中身を見て、AI と一緒にレビューする

Summary 画面の数字はあくまで件数の集計である。個別の指摘を開いて中身を見るのがレビューの本番である。

  1. 左サイドバーの 「Issues」をクリックするか、Summary 画面の指摘件数（例: 「16 Open issues」）を直接クリックすると、個別の指摘一覧に移る。
    • 左側の「Filters」で Software quality（Security / Reliability / Maintainability）ごとの内訳が確認できる
    • Severity でも絞れる。Blocker〜Info の5段階の緊急度で、Blocker が最も重大、Info が参考程度である
  2. 一覧から1件クリックすると、右側に 該当コードと SonarCloud による説明が表示される。上部に指摘内容・影響する Software quality・重大度（Blocker など）、下部のタブに切り替えると「Where is the issue?」（該当コード）・「Why is this an issue?」（理由の説明）が見られる

⚠️ ハマりどころ

  • SonarCloud の指摘には誤検知（false positive）もある。鵜呑みにせず AI と判断する
  • 解析対象を絞りたいので、このワークショップ用のリポジトリだけを対象にするのが推奨（Git ブランチ参照）
  • 意図しないリポジトリまで勝手に解析されることがある。原因は2つの組み合わせ:
    • SonarCloud の GitHub App を All repositories（全リポジトリ）で許可している
    • SonarCloud の Organization で新規リポジトリの自動取り込み（Automatic Analysis / auto-provisioning）が有効になっている

    この2つがそろうと、App から見えるすべてのリポジトリで、push のたびに SonarCloud が自動でプロジェクトを生成して解析する。プライベートリポジトリが含まれる場合はコードが外部に送られる。そのため All repositories は選ばない。

    誤って All repositories を選んでしまった場合は、次のどちらかで対処する。

    • 入口は https://github.com/settings/installations（メニューからたどるなら GitHub → Settings → Integrations → Applications → SonarCloud → Configure）。そこで Only select repositories に変更して対象を絞る
    • 個別プロジェクトだけ止めたいなら、SonarCloud の対象プロジェクト → Administration → Analysis Method の「Automatic Analysis」を OFF、または Administration → Deletion で削除

E2E テストの考え方

E2E（End to End）テストとは、本物のブラウザでアプリを操作し、画面から DB までを通して確かめるテストである。[6] のテストが部品を1つずつ台の上で検査するのに対して、E2E は組み上がったものに実際に乗ってみる。

[6] は経路の左半分と右半分を別々に固める（画面テストは HTTP をモック、API テストは外部 API をモック）。どちらのテストも自分の側の想定でモックを書くため、たとえばバックエンドが返すデータの項目名とフロントが読み取る項目名が食い違っていても、両方とも緑になる。実際に通信させて初めて、食い違いは「画面が空欄」のような形で現れる。この噛み合わせを確かめるのが E2E である。

E2E は [6] の置き換えではなく補完である。通して初めて破れが見える行だけをこの章で書き、それ以外の行は [6] の関数・API・画面のテストが引き取る。

[6] と [12] の守備範囲の違いを、実際に起きうるバグで見る
実際に起きうるバグ[6] のテスト[12] の E2E
フロントが項目名を綴り間違えて画面が空欄見逃す気づける
npm run build:front を忘れて古い画面が配信されている見逃す気づける
他人のメールで開いたとき前の人の購入の証が画面に残る見逃す気づける
画面に導線が無い API を直接叩くと、他人の購入の証が返る気づける（T-005 のように API を直接叩ける）見逃す（画面から辿れる操作しか書けない）
DB に保存された中身が壊れている（画面には表示されない）気づける（T-003 のように DB を直接見られる）見逃す（E2E が見るのは画面だけ）

Playwright とは

この E2E テストに使うのが Playwright である。ブラウザを実際に動かしてアプリを操作するテストツールで、付属の Codegen を使うと、自分が画面でやった操作がそのままテストコードとして書き出される。そのため、テストの書き始めでつまずかない。

流れ

工程やること
⓪ 準備Playwright を入れ、テスト対象のアプリを起動しておく
① テストする行を2本決める[6] ② の表から、ブラウザで確かめる行を選ぶ
② 操作を録画するCodegen で画面を操作し、操作をコードとして書き出す
③ 検証を足して実行する録画したファイルに「期待結果どおりか」を判定する行を AI に足させ、実行して結果を表に書く
④ 赤の原因を決める実装・テスト・決めていなかった仕様のどれが原因かを切り分ける（赤が出たときだけ）
⑤ push する実行結果の生成物を除いてコミット・push する

② と ③ が2段に分かれているのは、Codegen が書き出すのは操作の行だけで、判定（expect）を1行も書かないためである。かといって最初から AI にテストを丸ごと書かせると、AI は実装を読んで今の動きをバグごと正解にする。そこで、操作の骨格は録画で固定し、判定だけを [6] ② の表を根拠に AI に足させる。

このうち自分で考えるのは ① の行の選択、③ の検証の確認、④ の赤の判断である。ほかは Codegen と AI が進める。

1. テスト用ユーザを1人作る — Clerk ダッシュボードで作る。手順は4ステップである。

(1) メール認証を一時的に有効化する — Configure → User & authentication → Email。Google ログインしか有効にしていないと、次の画面でメール欄が使えない。「Sign-up with email」「Sign-in with email」を ON にして Save。

(2) Users タブで Create user を押す

(3) メールとパスワードを入れて作る

  • メールは e2e+clerk_test@example.com のように +clerk_test を付ける。付けないと「Enter a valid email address」で弾かれる
  • パスワードは任意である。通らなければ Ignore password policies にチェックを入れる。このパスワードは以降使わない（テストはログイン画面を通らないため）ので、どこにも保存しなくてよい

(4) メール認証を元に戻す — 同じ画面で両方 OFF にして Save。

2. 設定は AI に作らせる

@clerk/testing を使って、Playwright のテストを Clerk 認証済みの状態で走らせたい。

・テスト用ユーザのメールは環境変数 E2E_CLERK_USER_EMAIL から読む
・サインイン画面は操作しないこと（Google ログインなので自動操作できない）
・アプリの認証方式をあとから変えても壊れないようにすること
・認証状態は毎回のテスト実行時に作り直すこと
・認証状態のファイルは Git に入れないこと

下3行が効いている。「サインイン画面を操作しない」でログイン画面を通らない方式に、「認証方式を変えても壊れない」でパスワードや確認コードに依存しない方式に、「毎回作り直す」で期限切れしない作りに寄る。ファイル構成は指定しなくてよい。

3. 認証状態を作る — 環境変数を渡して実行する。

set -a; . ./backend/.dev.vars; set +a
export E2E_CLERK_USER_EMAIL='e2e+clerk_test@example.com'
npx playwright test --project=setup

これが緑になれば設定は正しい。ログイン画面を操作するコードが混ざっていれば、ここで止まる。

4. ② 操作の録画はこう起動する — 開いた瞬間からログイン済みになる。サインイン画面は出ない。

npx playwright codegen --load-storage=playwright/.clerk/user.json \
  -o tests/01-xxx.spec.ts http://localhost:8787/mypage

保存先のファイルは .gitignore に入れる（/playwright/.clerk/）。

⚠️ 手動でログインして --save-storage に保存する方法は取らないこと。

Google の画面を通るため、保存されるファイルに自分の Google アカウントのセッションが丸ごと入る。.google.com や .youtube.com のクッキーが数十個まとめて書き出される。

漏れたときの被害はアプリのアカウントではなく Google アカウントの乗っ取りである。しかも数日で期限切れになり、アプリが壊れていないのにテストが赤くなる。

上の方法なら保存されるのはこのアプリと Clerk のクッキーだけで、Google のものは入らない。

候補の行この2本に選べるか

② で録画したファイルは、操作を再生するだけでまだ何も確かめていない。判定（expect）が1行も無いため、このまま実行すると、画面の表示が間違っていても操作さえ通れば緑になる。表の「期待結果」どおりの画面になったかを判定する行が足されて、初めてテストになる。

埋めるのは < > の1箇所だけである。ファイル名に表の番号が入っているので、どの行かはそれで伝わる。あとの3行はそのままコピーする。

tests/<録画したファイル名> を、docs/TEST.md の「## テスト項目」の

・表の「前提条件」から始めて、「期待結果」を確かめて終わる形にする
・期待結果は表の文言だけを根拠にする。実装コードは読まないこと
・録画に入り込んだその場限りの値や外部サイトの URL は、何度実行しても通る形に直す

⚠️ 「このアプリのテストを書いて」と頼まないこと。

そう頼むと AI は実装を読み、今の動きをバグごと正解にする（「流れ」に書いた理由と同じ）。表だけを根拠にさせるため、2行目の「実装コードは読まないこと」を必ず入れる。

⚠️ 録画したときの画面の値が、そのまま埋まっていないか。

// 直したあと（購入の証の形を探している）

④ 赤の原因を決める（赤が出たときだけ）

やること: まず AI に原因を切り分けさせる。この時点では直させない（理由は [6] ⑤ テスト結果 と同じである。まとめて頼むと、AI はテストの期待値を緩めて緑にする道を選ぶ）。

[13] 自動デプロイ（Workers Builds）★★☆

お題: git push するだけで Cloudflare へ自動的にビルド・デプロイされる状態にする（[7] の手動デプロイを卒業する）
ツール: Cloudflare ダッシュボードの Workers Builds（Git 連携によるビルド・デプロイの自動化機能）
前提: [7] で wrangler deploy による手動デプロイまで完了していること
学び: CI/CD の初歩と、モノレポ構成でのビルド設定の考え方

他の Section 3 オプションと違い、ここでの作業はすべて Cloudflare ダッシュボード側の設定で完結する。リポジトリのコードに変更を加える必要は無く、Claude Code に実装を依頼する場面も無い。設定が一度終われば、あとは普段通り git push するだけで、Cloudflare 側が自動でビルド・デプロイを行ってくれる。

連携手順

  1. Cloudflare ダッシュボード → 対象の Worker → Settings → Build から GitHub リポジトリを連携する
    1. サイドバー最上部の 「Account home」 を選択する
    2. 画面中央（検索バーの下あたり）に並ぶ一覧から、対象の Worker を選択する
    3. 画面上部のタブを 「Settings」 に切り替える
    4. 下にスクロールし、「Build」セクション内の GitHub ボタンを選択する

    ⚠️ リポジトリのアクセス範囲について: GitHub ボタンを押すと GitHub 側で「Install & Authorize Cloudflare Workers and Pages」という許可画面が出る。

    ここでも SonarCloud のときと同様に、必ず 「Only select repositories」 を選び、連携したいリポジトリだけを許可すること。「All repositories」を選ぶとプライベートリポジトリのコードすべてに Cloudflare がアクセスできる状態になってしまう。

  2. Cloudflare に戻ると「Connect to a repository」画面が開く。上部の Git account で自分のアカウント（複数の GitHub 組織に所属している場合は連携したいアカウント）を指定する。Repository は直前に許可したリポジトリが自動で選ばれる
  3. Path（Root directory）を backend に設定する。モノレポ構成のため必要である。
    空のままにすると、Cloudflare が自動生成した誤った設定でデプロイされてしまう（詳細は下記ハマりどころ）
  4. Build command に npm install --prefix ../frontend && npm run build:front を設定する （フロントのビルドをここで行う。空のままだとフロントがビルドされない）
  5. Production branch を main に設定する（dev への push はプレビューのみになる）。
    ただし Git ブランチ の運用（dev→main マージ後に SonarCloud 解析）と組み合わせる場合は、マージがそのまま本番公開になる点に注意する。詳細は Git ブランチ を参照すること。

⚠️ ハマりどころ

  • Path（Root directory）を設定し忘れると、API が全滅する: このリポジトリは frontend/・backend/ に分かれたモノレポ構成になっている。
    そのため Path を空のままにすると、Cloudflare は「ルートに設定ファイルが無い」と判断し、cloudflare-workers-and-pages[bot] がリポジトリのルートに簡易的な wrangler.jsonc を自動生成して PR を送ってくることがある。
    この自動生成ファイルは静的配信専用で、API のルーティングも D1/KV のバインディングも含まない。だから誤ってデプロイされると /api/* が全滅（404）し、フロントも未ビルドの生ファイルが配信されてしまう。
    対策としてPath 設定を先に済ませ、もし該当 PR が来ていたらマージせずクローズすること
  • Build command を設定し忘れると、フロントがビルドされない: 既定の Deploy command は npx wrangler deploy だけで、これは vite build（フロントのビルド）を含まない。必ず上記手順4の Build command を設定する
  • デプロイ直後は数秒〜十数秒、変更が全世界のエッジサーバーに伝播しきっていないことがある。すぐにアクセスして 404 が出ても、少し待ってから再確認する

✅ 完了の定義

上記の連携手順を終えたら、何か軽微な変更（コメント追加など）をコミットして dev に push するだけで、Cloudflare ダッシュボードの Deployments に新しいビルドが自動的に現れることを確認する。これが確認できれば完了である。余裕があれば、dev → main にマージ・push し、本番 URL（workers.dev）にその変更が反映されるところまで確認する。

Workers Builds の動作確認用に、軽微な変更（コメント追加など）をコミットして dev ブランチに push して。

[14] 運用保守の自動化★☆☆

お題: 公開後の運用を体験する。扱うのは監視、ログ、障害特定、対策、コストの5つ
実装先: .claude/skills/（運用スキルを Claude Code に作らせる）
学び: 公開後の「運用」を Claude Code のスキルで仕組み化する

まず: Cloudflare API トークンを用意する

wrangler だけだと取得できる情報に制限がある。ログ集計やコスト試算には API トークンが要る。

  1. Cloudflare ダッシュボード右上のアイコン → Profile を選択する
  2. 左メニューの API Tokens → Create Token をクリックする
  3. 「Create Custom Token」の Get started をクリックする
  4. Token name を入力し、Permissions を Account / Account Analytics / Read にして作成する
  5. 取得したトークンを backend/.cf-ops.token に保存（例 CLOUDFLARE_API_TOKEN=... の1行）。.dev.vars とは別ファイルにする（理由は下記）。リポジトリのルートの .gitignore に backend/.cf-ops.token を追加しておく

このトークンは Worker が使うのではなく、運用スキルが shell からファイルを読んで使う（Cloudflare の集計 API（GraphQL）を叩くため）。

ここで注意したいのが置き場所である。.dev.vars は Section 1 のセキュリティ対策で Read を拒否しているので、スキルが cat 等で読もうとするとブロックされる。

そこで運用トークンだけは deny 対象外の別ファイル（.cf-ops.token）に置く。ここに入れるのは Analytics 読み取り専用の低権限トークンなので、Stripe/Clerk 等の高価値シークレット（.dev.vars）と分けても危険は増えない。

なお本番 secret に入れる必要はない（ローカルにあれば十分）。また、トークンが無くても wrangler tail のライブログは見られる。トークンが必須なのは集計・コスト試算だけである。

[5] で使った /code-review のように、インストールなしで最初から使えるものを「組み込みコマンド」と呼ぶ。
一方、Section 1 で入れた security-guidance のような「プラグイン」は、スキルなどをまとめて配布するパッケージである。

毎回同じ確認をスキル（.claude/skills/）にしておけば、「運用チェックして」の一言で再利用できる。ここで作ってもらうスキルは次の5つ。

付録: Claude Code 認証切り替えガイド

対象: 普段は API キーで使っている人が、一時的に Claude Code サブスクに切り替え、用が済んだら API キーに戻すための手順である。

これだけ覚える: どのキーを使うかは ~/.claude.json の記録で決まる。 rejected にあるキーは無視されてサブスクが使われ、approved にあるキーは使われる（サブスクより優先）。切り替えとは、この記録を /config や起動時プロンプトで書き換えること。

認証の記録は ~/.claude.json にある

「どのキーを使う / 使わない」は ~/.claude.json の customApiKeyResponses に記録される。 approved（使うキー）と rejected（使わないキー）の2つの配列があり、キーは末尾20文字だけが記録される（フルキーは保存されない）。

キーの3つの状態

状態意味起動時の挙動
approvedこのキーを使う、と承認済みこの API キーで動く（サブスクより優先）
rejectedこのキーは使わない、と拒否済みキーを無視してサブスクで動く
newまだどちらも選んでいない「このキーを使う？」と確認が出る

  1. Claude Code のセッション内でログアウトする（approved が空になり、古いサブスクのログインも消える）。 
    /logout

    claude

  4. 認証方式を確認する。claude.ai になっていれば成功である。~/.claude.json は approved が空・rejected に当該キーが入った状態になる。

  1. env に API キーがあることを確認する（無ければ設定）。普段 ~/.zshrc 等に書いてあるならそのままでよい。 
    export ANTHROPIC_API_KEY="sk-ant-xxxxxxxx"
  2. Claude Code を起動する。 
    claude
  3. API キーを有効化する。① の直後はキーが rejected に入っているため起動時プロンプトは出ない。/config を開き「Use custom API key」を ON にする（キーが未決定=new の場合は起動時に確認が出るので、そのときは「1. Yes」でもよい）。 
    /config
  4. 認証方式を確認する。API キー利用になっていれば成功である。~/.claude.json は approved に当該キーが入り rejected が空の状態に戻る（冒頭の ~/.claude.json の例と同じ状態）。 
    /status

一度「使わない」を選んでいると、キーは rejected に入っている。 /config の ON で自動的に approved へ移るので問題ない。手動でやるなら ~/.claude.json の customApiKeyResponses.rejected から 該当キーの末尾20文字のエントリを削除する（削除すると new に戻り、再度確認プロンプトが出る）。

症状原因対処
サブスクにしたのに API のままキーが approved に残っている/logout、または /config のトグルを OFF
API にしたいのに使われないキーが approved に無い（new/rejected）/config を ON、または起動時プロンプトで「使う」
ログインしても接続が切れるANTHROPIC_AUTH_TOKEN / CLAUDE_CODE_OAUTH_TOKEN が env に残存（承認ゲート無しで効く）該当変数を unset して再起動
/logout しても API が消えない/login で入力・保存したキー（keychain）は logout で消えない/status でソースを確認し、/login でサブスクに入れ直す

秘密情報の扱い: API キーの値をチャットやコードに貼らない。git 管理下のファイルにも書かない。恒久設定は各自の ~/.zshrc 等にとどめる。

仕組み（詳細・読まなくても切り替えはできる）

認証の優先順位

複数の認証情報があると、上ほど優先される。

順位認証方式
1クラウドプロバイダの資格情報（Bedrock / Vertex 等）
2ANTHROPIC_AUTH_TOKEN（Bearer トークン）
3ANTHROPIC_API_KEY — ただし approved のときだけ採用
4apiKeyHelper スクリプト
5CLAUDE_CODE_OAUTH_TOKEN
6サブスクの OAuth（/login で保存）

ANTHROPIC_API_KEY は承認ゲートがあり、未承認なら無視されてサブスクにフォールバックする。一方 ANTHROPIC_AUTH_TOKEN / CLAUDE_CODE_OAUTH_TOKEN はゲートが無く、セットされていれば効く。

/logout が実際にすること

  • customApiKeyResponses.approved を空にする（承認済みキーが外れる）
  • サブスクの OAuth 資格情報を消す
  • オンボーディング状態をリセット → 次回起動で確認プロンプトが再表示される
  • rejected には何も追加しない。/login で保存した keychain 上のキーも消さない

2つの「キーの保管場所」

  • 環境変数 ANTHROPIC_API_KEY … 承認（approved/rejected）で制御する。本ガイドではこれを前提とする。
  • 保存キー primaryApiKey（macOS Keychain）… /login でキーを直接入力した場合の保管先である。/logout では消えない。env 運用なら基本使われない。

補足: --bare / CLAUDE_CODE_SIMPLE などの簡易モードや非対話実行（claude -p）では、確認プロンプトを出さずに env のキーを直接使う経路がある（＝承認ゲートを通らない）。通常の対話起動は承認ゲート経由である。
