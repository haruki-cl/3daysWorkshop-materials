テスト工程ドラフト

このドラフトは、flow.html の [5] レビューと自動テスト の後半（自動テスト）を差し替えるために書いた。

工程の番号は、現行 [5] の ① レビューに続けて ②〜⑦ とした。

ゴールと考え方

ゴール: AI が書いたコードについて、「何を守れていて、何を守れていないか」を一覧で言える状態にする。

考え方: この工程は、テストを緑にすることを目標にしていない。 テストは、何も検査していなくても緑になる。 だから緑の本数を数えても、何を守れているかは分からない。 守るべきことを決め、一つずつ確かめて結果を書き残すところまでが、この工程である。

分担: 要件を決めるところから結果を判定するところまで、全部を AI に任せることはできない。 アプリを誰が使うか、何が起きたら困るかを知っているのは人間だけである。 そしてテストが落ちたとき、AI はアプリではなくテストのほうを緩めて通すことがある。 だから工程ごとに、AI に書かせる部分と人間が決める部分を分けてある。

全体の流れ

工程やることできあがるもの
②AI と壁打ちして、守られるべきことを箇条書きにするTEST.md の「テスト要件」
③要件ごとに「どこが壊れていたら守られないか」を挙げ、表にするTEST.md の「テスト項目」
④表で指定した種類の分だけ実行環境を用意するVitest の設定
⑤表を渡してテストコードを書かせるテストファイル
⑥バックとフロントそれぞれで実行する実行結果
⑦表の結果列を埋め、落ちた原因を切り分ける結果入りの表

② テスト要件を決める（Why）

流れ

  1. Claude Code に壁打ちを頼む。前提を人間が先に整理しておく必要はない。 
    このアプリのテスト要件を決めたい。壁打ちに付き合ってほしい。

まず、要件を決めるために必要なことを私に質問して。
わからないことは推測せず、必ず質問すること。

決まったら docs/TEST.md の「## テスト要件」に箇条書きで書いて。
各項目は「〜してはいけない」「〜は必ず」の形にすること。

    「わからないことは推測せず質問して」の一行がないと、AI は「一般利用者向けの公開サービスと仮定して」と書いて先に進む。 前提を想像で埋めれば、そこから導く要件も想像になる。

  2. 出てきた項目を、載せる基準にかけて取捨する。基準は破られたら何が起きるかを1行で言えること。
    項目破られたら判定
    他人のライセンスキーが返る買っていない人が使える。個人情報が漏れる載せる
    購入したキーが消える金を受け取ってモノを渡していない状態になる載せる
    レスポンスが遅い言えない（何秒から問題かを決めていない）載せない
    エラーが出ない言えない（何も起きていない状態と区別できない）載せない
  3. docs/TEST.md がこの形になったら ② は終わり。 
    ## テスト要件

- ライセンスキーとメールアドレスを本人以外に返さない
- 購入が成立したらライセンスは必ず発行され、再読込しても消えない
- ユーザが登録される
- 認証が必要な API は未認証のアクセスを拒否する
- 必須項目が空の入力を受け付けない

ポイント

  • ここで出た要件が以降すべての土台になるので、モデルは高精度なもの（Fable / Opus）を使う。
  • 書き終えた「## テスト要件」は、③ 以降で AI に書き換えさせない。 上書きされると、③ で項目を判定する根拠と、⑦ で原因を帰属させる根拠が消える。
  • 要件を数え上げきることは目標にしない。 数え上げたかどうかを確かめる手段がないので、いくら時間をかけても終わったと判断できない。

③ 何をテストするかを決める（What）

流れ

  1. Claude Code に表を書かせる。 
    docs/TEST.md の「## テスト要件」と SCREEN_SPEC.md を読んで、
同じファイルに「## テスト項目」として表を追記して。

・要件1つについて「どこが壊れていたらこの要件が守られないか」を挙げ、
  挙げた場所ごとに1行を作る
・列は「番号 | 守る項目 | どこで確かめる | 前提条件 | やること | 期待結果 | 結果」
・「どこで確かめる」は 関数 / API / 画面 のどれか
・見る場所が違えば別の行にする（レスポンスを見る行と DB を見る行は分ける）
・前提条件は空欄にしないこと
・「結果」列は空欄のままにする
・「## テスト要件」は読むだけ。書き換えないこと
・期待値の根拠は要件と SCREEN_SPEC.md の記述に置き、実装コードから推測しないこと

    このプロンプトの中心は、どこが壊れていたらこの要件が守られないかを挙げさせるところにある。 「ユーザが登録される」なら、フォームが送信していない、API がリクエストを処理していない、DB に入っていない、入ったものが読み出せない、の4か所が出る。 このうち1か所でも壊れれば、ユーザは登録できない。 だから挙げた場所ごとに1行を作る。 API だけ確かめて済ませると、送信ボタンが繋がっていないことに気付けない。

  2. こういう表になる。
    番号守る項目どこで確かめる前提条件やること期待結果結果
    T-001ユーザが登録される画面登録フォームを表示有効な値で送信登録 API が呼ばれる
    T-002ユーザが登録されるAPIDB が空POST /api/users201 が返る
    T-003ユーザが登録されるAPI同上POST 後に DB を直接見るレコードが1件ある
    T-004ユーザが登録されるAPIT-003 の状態GET /api/users/:id保存した値が返る
    T-005キーを本人以外に返さないAPIA 購入済み、B 未購入B でライセンス取得 APIA のキーが返らない
    T-006キーを本人以外に返さない画面同上B でマイページを開くA のキーが出ない
  3. 人間が確認する。見るものが2つあるので、順番に見る。
    順見るものやること
    1観点の抜け挙げた場所が足りているか。「ユーザが登録される」に DB の行がない等
    2テストしなくていい箇所挙げた場所のうち、確かめるコストに見合わないものを落とす

    1 と 2 を同時に見ると、片方が浅くなる。 足りない行を探す作業と、多すぎる行を削る作業は、向きが逆だからである。 1 を確定させてから 2 に入る。 落とした行には、落とした理由を1行残す。

「どこで確かめる」の3種

この列が、原案でいう「テストスイートの指定」に当たる。 npm test が3つ並ぶのは、テストを走らせるランナーが同じで、その下の実行環境だけが違うからである。 環境と必要なパッケージは ④ で用意する。

語叩く場所見る場所コマンド
関数関数を直接呼ぶ戻り値npm test
APIHTTP リクエストを投げるレスポンスと DBnpm test
画面React を描画して操作描画された内容npm test

同じ「API」でも、T-002 と T-003 は別の行になる。 T-002 はレスポンスを見て、T-003 は DB を見る。 API が 201 を返しても、DB に書けていないことはある。

本物のブラウザで画面からデータベースまで通すテストは、この工程に含めない。 Section 3 の [12] E2E テストで扱う。

ポイント

  • 前提条件の列を空欄のまま ⑤ に進めない。 空欄だと、AI は初期状態を用意するコードを書かない。 前のテストが残したデータがそのまま残り、テストはそれを見て通ってしまう。
  • 確かめる場所は、実行が速く書く手間も小さいほうから選ぶ。 関数がいちばん軽く、API、画面の順に重くなる。 同じことを確かめられるなら、軽いほうを選ぶ。
  • 要件を壊れる場所ごとに行に分けておくと、⑦ で落ちた行がそのまま原因の場所を指す。 1本のテストで画面からデータベースまで通してしまうと、落ちたときにどこが原因か分からない。
  • 番号は、AI にテスト名の先頭へ入れさせる。 ⑦ で表の行とテストコードを番号で照合するために使う。

④ テストスイートを用意する

③ の表の「どこで確かめる」列に出てきた種類だけを用意する。 「関数」の行しかなければ、画面テスト用のパッケージは入れない。

docs/TEST.md の「## テスト項目」の「どこで確かめる」列を見て、
必要なテスト環境だけを用意して。

・関数・API のテスト（backend/）: @cloudflare/vitest-pool-workers を使い、
  設定は cloudflareTest プラグイン方式で書く
・画面のテスト（frontend/）: 同じ Vitest を jsdom 環境で使い、
  @testing-library/react で描画・操作する
・表に出てこない種類の環境は入れないこと

⑤ テストコードを書かせる（How）

docs/TEST.md の「## テスト項目」の表に従ってテストを実装して。

・テスト名の先頭に表の番号を入れる（例: test('T-003 POST 後に DB にレコードが1件ある', ...)）
・「期待結果」列の値をそのまま使い、実装コードから推測しないこと
・表にない項目を勝手に足さないこと
・test.skip / it.todo / it.only を使わないこと
・固定待ち（waitForTimeout）を入れないこと
・外部サービスへの fetch はすべてモックすること

番号をテスト名の先頭に入れておくと、⑦ で表とテストコードを grep だけで突き合わせられる。

⑥ 実行する

バックとフロントは別パッケージなので、それぞれのディレクトリで実行する。

cd backend  && npm test
cd ../frontend && npm test

出力の skipped が0件であることを、人間が自分で見る。 skip や todo が付いたテストは実行されない。 実行されなかった分は失敗として数えられないので、本数が足りないまま「全部緑」と表示される。

ここでコミットする

⑦ でテストファイルの差分を見るが、git に追跡されていないファイルは差分が出ない。 先にコミットしておかないと、テストが改変されていても気付けない。

docs/TEST.md とテストコードとテストの設定をコミットして。
このあと git で確認するので、私が言うまで追加のコミットはしないこと。

⑦ 集計して原因を切り分ける

流れ

  1. 表とテストコードを番号で突き合わせる。 
    docs/TEST.md の表にある番号と、テストコードのテスト名に入っている番号を
grep で抽出して diff で突き合わせて。

実行したコマンドと出力をそのまま見せること。要約しないこと。
判定はこちらでする。
    • 表にあってコードにない → ③ の項目が ⑤ で落ちている
    • コードにあって表にない → AI が勝手に足している
  2. 落ちた原因を切り分けさせる。この時点では直させない。 
    落ちているテストの原因を切り分けて。
実装が要件を満たしていないのか、テストの書き方（ロケーター・期待値）が
悪いのか、それぞれについて判定だけ報告して。
まだ何も直さないこと。

    診断と修正を1回のやりとりでまとめて頼むと、AI はテストの期待値を緩めて緑にする道を選べる。 実装を直すより手数が少ないからである。 判定だけを先に受け取り、どちらを直すかは人間が決める。

  3. 判定に応じて表の「結果」列を埋める。
    番号守る項目結果
    T-002ユーザが登録される緑 → 保証できる
    T-003ユーザが登録される落ちた → 保存処理が未対応
    T-005キーを本人以外に返さない落ちた → 認可の抜け（バグ）

    要件を壊れる場所ごとに分けて行にしてあるので、落ちた行がそのまま原因の場所を指す。 T-001 が落ちたなら画面、T-003 が落ちたなら保存処理である。

  4. 直す対象を指示する。テストファイルは変更禁止だと明示する。 
    T-005 の原因は認可の抜けなので、backend の実装を直して。
テストファイルは変更しないこと。
  5. 修正後に、テストファイルが変わっていないことを人間が見る。 
    git diff --stat -- '*.test.ts' '*.test.tsx'

    ここに差分が出ていたら、直されたのはアプリではなくテストである。

完了したら push する

手順5 の差分確認が終わってから push する。 ここまで追加のコミットを止めていたので、残っている変更をまとめる。

テスト工程の作業をコミットして dev ブランチに push して。

ポイント

  • 落ちた原因が実装か、テストか、要件かを切り分ける作業は、この工程でいちばん推論を要する。 モデルは ② と同じく高精度なものを使う。
  • 全部が緑にならなくてよい。 落ちた行は「作ったつもりが作られていなかった」という発見であり、表に残せばそれも成果になる。

✅ 完了の定義

  • docs/TEST.md に「テスト要件」と「テスト項目」の表があり、各行の「前提条件」が埋まっている
  • 表の番号とテストコードのテスト名が一致している（どちらか片方にしかない番号がない）
  • npm test の出力に skipped が0件
  • 表の「結果」列がすべて埋まっている（緑／落ちた＋原因）
  • 落ちた項目を直した場合、テストファイルに差分が入っていない

⚠️ ハマりどころ

  1. 「テストを通して」と頼んでしまう。 アプリに問題があるときでも、AI はテストの期待値を緩めて応じることがある。 診断を頼むターンと、修正を頼むターンを分ける。
  2. 前提条件が空欄のまま ⑤ に進む。 前のテストが残したデータを見て緑になるので、実装が壊れていても気付けない。
  3. AI が「画面」に寄せる。 画面を操作すれば何でも確かめられるように見えるため、行の割り当てを任せると画面が増える。 「どこで確かめる」は人間が決める。
  4. AI が要件を書き換える。 同じ TEST.md に追記していくので、黙っていると「テスト要件」ごと整形し直す。 「読むだけ」を毎回プロンプトに書く。
